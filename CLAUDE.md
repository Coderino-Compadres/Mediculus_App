# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

Mediculus is a mental-health / wellbeing tracking platform (emotion diary, DBT technique tracking, mood scales) aimed at patients (including minors, via a parent/guardian account), specialists (psychotherapists, dietitians), and their supervising organization. All three account types now have a view of their own: the patient app, the guardian's `/parent`, and the specialist's `/specialist` (caseload → weekly reports, guardian-account invitation codes, and writing into the technique catalogue). The domain model is designed (see `ERD/DIAGRAM.drawio*`), registration/login work end to end (DRF endpoints under `/api/auth/`, wired to the React pages), and the patient app both reads and writes its own diary (`/api/diary/today/` for the entry form, plus `/api/dashboard/home/`, `/api/diary/`, `/api/analysis/frequency/` and `/api/reports/` for the screens that read it). The diet module has its first endpoint of any kind, `/api/diet/hydration/`, behind `/diet/hydration` — everything else in that module is still screens over empty shapes. Weekly reports are generated (`/api/reports/`, including a PDF export) but **derived, not stored**: nothing has ever written a `raport` row, which is why the home screen's technique suggestion could only ever have shown seed data — and why that card has now been taken off the screen.

Repo layout:
- `backend/` — Django project (`config/` settings/urls) plus one app, `core/`, holding all domain models across both databases (see Architecture).
- `frontend/` — Vite + React PWA scaffold (`vite-plugin-pwa`).
- `scripts/` — hand-written SQL that defines and seeds the actual database schema (see below — this is not Django migrations).
- `ERD/` — entity-relationship diagram for the two databases.
- `markdown/` — internal planning/requirements notes (Polish); not code documentation.

## Architecture

**Two independently-managed Postgres databases**, both configured in `backend/config/settings.py` `DATABASES`:
- `default` → `user_db` — identity/PII data: `user`, `user_role`, `specjalist`, `patient`, `parent_child`.
- `medical` → `medical_db` — pseudonymized clinical data: `diary`, `mood_scale`, `technique`, `raport`, `hydration`.

The split is intentional (data pseudonymization): `medical_db` rows reference patients only via `patient.id_medical`, a UUID that is **not** a real foreign key across databases — it's a logical/application-level join only (see comments in `scripts/database_setup.sql`). Never assume Postgres will enforce referential integrity between the two DBs; that has to be handled in application code.

**Domain schema lives in Django models + migrations (app `core`).** `backend/core/models.py` mirrors `scripts/database_setup.sql` (same table/column names via `db_table`/`db_column`). All models live in a single app spanning both databases, and `core/routers.py` (`CoreDatabaseRouter`, wired via `DATABASE_ROUTERS`) maps them by name: everything in `MEDICAL_MODELS` goes to `medical`, the rest to `default`. The router implements `db_for_read`/`db_for_write`, so `Diary.objects.all()` reaches `medical_db` on its own — `.using('medical')` is no longer required (it still works, and is harmless to keep).

Data migrations in `core` need care: `allow_migrate` receives `model_name=None` for `RunPython`/`RunSQL`, so pass `hints={'target_db': 'default'}` (or `'medical'`) on those operations to pin them to one database. Without a hint they run against **both**, which fails loudly rather than being silently skipped — see `core/migrations/0002_align_faked_schema.py` for the pattern.

Two DBs mean two independent migration histories: run `python manage.py migrate core --database=default` for the `user_db` models and `python manage.py migrate core --database=medical` for the `medical_db` models — a plain `migrate core` only targets `default`.

`0001_initial` is applied as **faked** everywhere, because `scripts/database_setup.sql` had already created the tables. Consequences worth knowing:

- Setting up a new environment means running `database_setup.sql` + `mock_data.sql` first, then `migrate --fake-initial` on both databases (`markdown/serwery.md` has the exact sequence). Letting migrations create the schema from scratch instead would work, but then `mock_data.sql` fails — its INSERTs omit `created_at`/`updated_at`, which only have database defaults in the SQL script, not in the Django-generated schema.
- Faking means Django cannot see drift between the two "sources of truth". `0002_align_faked_schema` exists precisely because `database_setup.sql` had shipped `TIMESTAMP`/unbounded `VARCHAR` where the faked state recorded `timestamptz`/`varchar(255)`. If you change one of the two, check the other by hand — `makemigrations` will not warn you.

`0011`–`0013` are the specialist view's schema, and they follow the same `SeparateDatabaseAndState` + `IF NOT EXISTS` pattern: `0011_specjalist_patient_invitation` adds `patient.id_specjalist_pending` and `patient.specjalist_accepted_at` (user_db) — the invitation half of `patient.id_specjalist`, which until then was written by `mock_data.sql` and by nothing else; `0012_parent_invitation` creates `parent_invitation` (user_db), a specialist-issued code a guardian registers with; `0013_technique_catalogue` widens `technique` to the shape the catalogue actually has (medical_db, so its `RunSQL` carries `hints={'target_db': 'medical'}`) — slug, subtitle, `schools`/`steps` as JSONB, DBT group and module, availability, duration, `description_ready` and `author_id_specjalist`. Two defaults in `0013` are load-bearing: `description_ready` defaults to **FALSE**, or the four half-rows `mock_data.sql` seeds would have been published to every patient's catalogue the moment it ran; and `author_id_specjalist` is a plain UUID column rather than a FK, because `technique` is in medical_db and `specjalist` in user_db — the same logical-only join as `diary.id_medical`. `0014_must_change_password` is the same pattern once more (user_db, `hints={'target_db': 'default'}`): one `BOOLEAN NOT NULL DEFAULT FALSE` on `"user"`, deliberately **not** backfilled, because every account that predates it chose its own password at registration — FALSE is the true answer for all of them rather than an approximation. It is set in exactly one place, `core/colleagues.py`, and cleared in exactly one, `PasswordChangeSerializer.save`. `0015_hydration` creates the diet module's first table (medical_db, `hints={'target_db': 'medical'}`): a row per serving — `id_medical`, `entry_date`, `drink`, `amount_ml` — rather than a `glasses` counter, because a counter makes "+1 szklanka" a read-modify-write two taps can lose and leaves a mis-tap uncorrectable. `entry_date` is a column rather than derived from `created_at` (the way `diary` derives its day) for one reason: the diary answers that question once per row in Python, while this table is grouped by day seven days at a time, so a date column plus `(id_medical, entry_date)` keeps the chart one indexed query. `core/days.py` still decides where the boundary is. `0016_diet_meals_supplements` is the rest of that module, three tables in medical_db under the same pattern and the same hint: `diet_meal` (the food diary — `entry_date`, a nullable `kind` and `eaten_at`, and a `description` that may be empty, because §05's rule is that no field blocks a save, and deliberately **no** portion, weight or calorie column, because §04 states that scope outright), `supplement` (§08's list — name, dose, frequency, hour, start/end dates, `reminder_enabled`; only `name` is NOT NULL) and `supplement_intake` (one tick per preparation per day, `UNIQUE (id_supplement, entry_date)` so a double-tapped checkbox is one row). There is deliberately **no `diet_day` table**: a day has nothing of its own to store that is not derivable from its meals, and one would only be a second answer to "how many meals did Tuesday hold". And `supplement_intake.id_supplement` is a **real foreign key**, unlike every `id_medical` in medical_db — both tables are in the same database, so Postgres can enforce it, and CASCADE is right because a tick belongs to the preparation it ticks off. The pseudonymized, application-only join is the one that crosses databases.

Both Azure databases were at `0001` (faked) when that was last checked, on 2026-08-28 — the date is part of the claim, because nothing in the repo tracks the deployment's migration state and `0009` was added later without re-checking it; `DJANGO_ENV_FILE=.env.azure python manage.py check_databases` is what answers it for real. `0002`–`0009` have only been applied locally and need `migrate` on Azure — **on both databases**, which is the trap: a plain `migrate core` targets `default` only, and a `medical` left behind at `0004` fails with `column diary.tension_level does not exist` on the first request to `/api/dashboard/home/`. Four of them are written as `SeparateDatabaseAndState` with `ADD COLUMN IF NOT EXISTS`, because `database_setup.sql` declares the same columns and the documented setup order runs that script first: `0004_user_consents` adds the two RODO consent timestamps to `"user"`, and `0005_diary_entry_fields` adds the columns the "Dodaj wpis" form needs — `tension_level`, `emotion_note`, `thought`, `risky_behavior_note` on `diary`, plus `shame_scale`/`calm_scale` on `mood_scale`. `0005` targets medical_db only, so its `RunSQL` carries `hints={'target_db': 'medical'}`. `0006_drop_overall_feeling` then removes `diary.overall_feeling`: the "jakość samopoczucia" slider that would have filled it was cut from the entry form and `current_mood` already records how the patient says they feel, so it was a duplicate with no source. It is the first destructive migration — the text `mock_data.sql` used to seed there is not recoverable by reversing it. `0007_parent_child_accepted_at` adds `parent_child.accepted_at` (user_db, so `hints={'target_db': 'default'}`): NULL is a guardian invitation nobody has answered, set is the moment it was accepted — see the guardian-invitation notes below for why a refusal deletes the row instead of filling a third column. `0009_diary_time_of_day` adds `diary.time_of_day` (medical_db, so `hints={'target_db': 'medical'}`), the entry form's "pora dnia" question — one of `morning`, `noon`, `evening`, `night`, or NULL. It closes a **silent data loss**, not a missing feature: the form had been sending the key for a while and `DiaryEntrySerializer` is a plain `serializers.Serializer`, which discards a key it does not declare *without an error*, so the patient picked "Wieczór", was told the entry had been saved, reopened it and found the question blank. Which is why the serializer now names the field as a `ChoiceField` rather than accepting free text: an answer outside the four buckets is a 400, and the one thing it must never be again is quietly dropped. Deliberately **not** backfilled — nothing in an older row says what time of day it describes, so NULL there is the correct value rather than a gap to fill. The vocabulary lives in `core/time_of_day.py` and holds **only** the four keys: 'Rano'/'Południe'/'Wieczór'/'Noc' belong to `frontend/src/utils/timeOfDay.ts`, and a second copy in Python would be one that can quietly disagree — the opposite arrangement to `emotions.py`, where the Polish name *is* the stored value. `test_time_of_day.py` now pins the two lists together the way `test_emotions.py` pins the emotion names — it parses `TIME_OF_DAY_OPTIONS` out of the `.ts` file and compares the four values *and their chronological order* in both directions, so a rename on one side alone fails a test instead of becoming a 400 on save and a blank chip on read. The ERD (`ERD/DIAGRAM.drawio`) was brought back in step with `0006` and now lists `diary` and `mood_scale` in the same order as `database_setup.sql`, `time_of_day` included — `0009` added that row to the `.drawio` by hand. The diagram is now **fully in step with the models**: `0011`–`0013` were drawn into `ERD/DIAGRAM.drawio` by hand along with the whole backlog `KNOWN_ERD_GAPS` had accumulated (the four consent columns, `patient.id_medical`, `parent_child.accepted_at`, `raport.id_technique`), plus the new `PARENT_INVITATION` entity and edges for the new relationships — dashed for `technique.author_id_specjalist`, this diagram's convention for a reference Postgres does not enforce because the two tables live in different databases. `0016`'s three tables (`DIET_MEAL`, `SUPPLEMENT`, `SUPPLEMENT_INTAKE`) were drawn in the same way, with the two `id_medical` edges dashed and `supplement_intake → supplement` solid — a real FK, because both tables are in medical_db. **`KNOWN_ERD_GAPS` is therefore empty, and keeping it empty is the point**: `test_erd_sync.py` parses the `.drawio` XML and compares it column-for-column with the models in both directions, so a schema change now fails a test until the picture catches up. If one genuinely cannot be drawn immediately, add the entry *with the reason*. What is still behind is the **`.png`/`.pdf` exports**, which are generated by hand (there is no drawio CLI on the dev machine) and which nothing checks at all — they are behind on everything since `0004`.

Also be aware there will be two parallel notions of "user" in `user_db`: Django's own `auth_user` (created by `manage.py migrate` for the built-in apps, used only for `/admin/` login) and `core.User` (the hand-mirrored `"user"` table, the actual domain/app user). They are intentionally not connected — don't conflate them.

A few `on_delete` choices in `core/models.py` are a deliberate improvement over the raw SQL, which specifies no `ON DELETE` action (i.e. Postgres `NO ACTION` everywhere): `User.user_role` and `Raport.technique`/`Patient.specjalist` use `PROTECT`/`SET_NULL` instead, chosen per-relationship for sane application behavior rather than mirrored verbatim.

**Env-var-driven settings, no defaults for required values.** `settings.py` reads `DJANGO_SECRET_KEY`, `DJANGO_DEBUG`, and all `USER_DB_*` / `MEDICAL_DB_*` DB credentials via `os.environ[...]` (not `.get`), so the process will hard-fail at import time if any are missing — always ensure `.env` is populated (see `.env.example` for the full list) before running anything backend-related. `CORS_ALLOWED_ORIGINS`, `CSRF_TRUSTED_ORIGINS` and `DJANGO_ALLOWED_HOSTS` are optional comma-separated lists (whitespace around entries is stripped; origins must include a scheme). Two optional flags default to their Azure-safe value, so the deployment needs no App Setting for either: `DB_SSLMODE` (default `require`; set `disable` for the local container) and `DJANGO_USE_PROXY_SSL_HEADER` (default `true`; set `false` for a directly-reachable server, since otherwise a client can spoof `X-Forwarded-Proto` and make `request.is_secure()` lie).

**Authentication: DRF endpoints under `/api/auth/`, session cookie, custom user table.** `core/urls.py` (mounted at `api/` by `config/urls.py`) exposes `csrf/`, `register/`, `login/`, `logout/`, `me/`, `guardian/`, plus `/api/guardian/invitations/` and `/api/account/` (see the profile section below). The pieces worth knowing before touching them:

- **`core.User` is not an auth user.** `django.contrib.auth.login()` would write an `auth_user` primary key into the session, so it is unusable here. `core/authentication.py` borrows only the session framework: `start_session()` stores the domain user's id under `core_user_id`, and `SessionUserAuthentication` (the project-wide `DEFAULT_AUTHENTICATION_CLASSES`) reads it back. `core.User` carries an `is_authenticated = True` class attribute purely so DRF's `IsAuthenticated` can duck-type it.
- **`IsAuthenticated` is the default permission** and `UNAUTHENTICATED_USER` is `None`, so a new endpoint that declares no `permission_classes` is closed rather than accidentally public. `CsrfView`/`RegisterView`/`LoginView` opt out explicitly.
- **CSRF applies to `register/` and `login/` too**, via a hand-applied `@csrf_protect` — DRF marks every `APIView` csrf_exempt, and the usual enforcement lives in the authentication class, which does nothing for a caller who has no session yet. `GET /api/auth/csrf/` both sets the cookie and returns the token in its body; the body copy is what a frontend on another site uses, since it cannot read the API's cookies.
- **A rejected CSRF check answers in JSON** (`CSRF_FAILURE_VIEW` → `core/csrf.py`), because Django's own failure view renders HTML that a `fetch()` cannot read — the frontend was falling back to a generic "something went wrong" and discarding the only useful detail. The technical `reason` is included only when `DEBUG`; in production it goes to the log instead, which is also why `settings.LOGGING` exists: Django's default console handler carries a `require_debug_true` filter and the only other one mails admins about `ERROR`s, so a CSRF rejection (a `WARNING`) reached **nothing at all** with `DEBUG=False`.
- **Login answers identically for a wrong password and an unknown address**, and spends the same time on both (`_get_unmatchable_hash` in `core/serializers.py`) — for a mental-health service, who has an account is itself sensitive. `_password_matches` also survives the literal `'mock_hash_placeholder'` that `mock_data.sql` seeds, which would otherwise make `check_password` raise.
- **Only the field that belongs to the chosen account type is sent.** `specialization` and `invitation_code` are rendered conditionally but their values live in one form state that survives a change of account type, so somebody who typed a code as a guardian and then switched to "konto pacjenta" was still sending it — the backend refused (correctly: a code that quietly did nothing would look like it had worked), the error came back under `invitation_code`, and that input was no longer on screen. The registration failed with **no visible message at all**. `Register.tsx` now picks the payload from the account type; the backend's refusal stays as the backstop for a hand-made request.
- **The registration form's "account type" choice drives the schema**, via `ACCOUNT_TYPES` in `core/serializers.py`: `patient` → role `patient` + `Patient(is_child=False)`, `minor_patient` → role `patient` + `Patient(is_child=True)`, `parent` → role `rodzic` and **no `Patient` row at all** (a guardian is not a clinical subject, so they get no `id_medical` and nothing in `medical_db` can refer to them). Each entry carries a `profile` key naming which side table it gets, which is what `create()` switches on. **The `parent` entry is not self-service, and the enforcement is a rule rather than its absence from the list**: `_check_invitation` now refuses a guardian registration carrying no code (`INVITATION_REQUIRED`, under `invitation_code` so the message lands on the input that produced it), and a blank or whitespace code counts as none — the field is `allow_blank`, so `''` must not read as "no code given". The type has to stay on the list because redeeming a code *is* a registration: the account is created by this serializer, inside the transaction that spends the invitation. The reason mirrors the specialist one exactly — a guardian account asserts that this person is a child's legal guardian, the app cannot check that, and the treating specialist who sat with the family can. The knock-on effect is worth knowing: **a guardian account is now never created unattached**, it is born linked to one child and already accepted, which leaves `POST /api/auth/guardian/` for the further children of a parent who already has an account. The requirement is on the pair (account type, code) rather than on the field, or a patient would be asked for one too; `validateInvitationCode` in `frontend/src/utils/validation.ts` mirrors it so the form says so before the round trip, and `Register.tsx` puts the sentence *above* the input, because a code is something you either were given or have to go and ask for. One row does not follow the rule and cannot: `scripts/mock_data.sql`'s guardian, since SQL does not pass through the serializer. **There is no `specialist` entry any more, and its absence is the enforcement.** A specialist used to sign up here, which was safe as far as *access* goes — the role grants nothing on its own — but wrong about the claim the account makes: the app cannot check anybody's qualifications, and an existing specialist can. So a professional account is created in the panel instead (`core/colleagues.py`, `POST /api/specialist/colleagues/` — see the specialist section below), and `account_type: 'specialist'` in a hand-made body is an `invalid_choice` 400 rather than a specialist. The two rules that outlived that branch moved with it: `SPECIALIZATION_REQUIRED` and `SPECIALIST_MUST_BE_ADULT` are module-level constants now, read by `SpecialistColleagueCreateSerializer`, because they were rules about a specialist account rather than about the form that used to hold them. `free_email` and `checked_date_of_birth` were extracted at the same time and are shared by both forms — two copies of "this address is taken" are two copies free to disagree. `patient.id_specjalist` is still not self-assignable and nothing must be added that writes it directly. `is_child` comes from that choice, not computed from `date_of_birth`, but `_check_age_matches_account_type` refuses the two combinations where they would contradict each other (an adult date on a `minor_patient`, a minor's date on a `patient`) — otherwise a later feature trusting one column over the other would silently be wrong about some records. The boundary lives in `ADULT_AGE`, a policy constant rather than a fact: RODO art. 8 uses 16 for consent to digital services, so it may need revisiting. A `parent` is deliberately not age-checked — asserted in two halves now that a code is required, since a guardian registration with a minor's date of birth is refused for the *code* rather than the age (`test_auth_api` pins the refusal naming only `invitation_code`, `test_parent_invitation_api` the 201 with a code). Roles are looked up by name and come from `mock_data.sql`, not a migration, so a database missing the row yields `role: null` rather than a failure.
- **A minor's account is blocked until a guardian accepts it.** Two halves, and the split is the point — naming somebody is a request, accepting is the consent a minor cannot give for themselves (RODO art. 8):
  - `POST /api/auth/guardian/` (the child) names the guardian by e-mail and creates a `parent_child` row with `accepted_at` NULL. **The address has to belong to an account whose role is `rodzic`** — `GUARDIAN_ROLE` in `core/serializers.py` reads that name out of `ACCOUNT_TYPES` so the registration form and this one cannot disagree. A patient's address, a specialist's, an account with no role and an address nobody registered all get the **same** rejection: telling them apart would turn the form into a way to ask who has an account here and of what kind. The child's own address is the one exception, answered specifically (mirroring `parent_child_not_self`) because it is a mistake they can act on. One pending invitation at a time, so a child cannot fish for whichever adult answers first; re-sending it to the same guardian is idempotent. **`validate()`'s order is load-bearing:** `ALREADY_LINKED`/`ALREADY_INVITED` describe the child's own account and are raised *before* the role is looked at, because the other way round a child holding any link got `ALREADY_INVITED` for a `rodzic` address and `NOT_A_GUARDIAN` for everything else — a working probe for whether an address is a guardian account, which is precisely what the shared message exists to prevent. It also equalizes the query count across addresses, so the answer does not leak by timing either.
  - `DELETE /api/auth/guardian/` (the child) withdraws a *pending* invitation, so a mistyped address that happens to belong to a real guardian is not a dead end. It refuses once accepted: undoing a link is not the child's decision, or the guardian's oversight would last exactly as long as the child allowed it.
  - `GET /api/guardian/invitations/` + `POST .../<uuid>/accept/` + `POST .../<uuid>/reject/` (the guardian). Filtered by `parent=request.user`, so somebody else's invitation answers exactly like a nonexistent one (404 — a 403 would confirm it is real), the same convention as `/api/diary/<id>/`. Accepting twice succeeds (a double-clicked button); **refusing deletes the row** rather than marking it refused, which puts the child back to naming somebody else instead of leaving them with a "no" nobody can act on. An already-accepted link is not refusable here — withdrawing one is a different decision, with a live account behind it, and belongs to the parent panel.
  - The rules live in `core/guardian.py`, out of the views so they can be tested without a request. `accepted_at` is a timestamp rather than a boolean for the same reason as the consent columns on `user`: RODO art. 7(1) puts the burden of proof on us and "yes" without a date proves nothing.
- **`UserSerializer.guardian_status` is what gates the frontend**: `'none'`, `'pending'` or `'accepted'`, and `null` for everyone the question does not apply to (an adult patient, a guardian, a specialist). Only `'accepted'` unblocks the app. `App.tsx`'s `RequireAuth` sends any other minor to `ROUTES.linkGuardian` and `RequireGuardianLink` pushes everyone else off that screen; `needsGuardianLink` in `src/api/auth.ts` deliberately **fails closed** on `null`, since letting an unvouched-for child write health data is the worse way to be wrong. `LinkGuardian.tsx` has two states off the same status — the form, then the wait (check-again / withdraw, and nothing that could accept on the guardian's behalf).
- **The gate is enforced on the API too, in `_require_patient` (`core/views.py`).** It used to live only in `App.tsx`'s route guard, so a hand-made request from an unlinked minor's session reached the diary, the dashboard and the reports — and RODO art. 8 makes a minor's consent the guardian's to give, not something a route guard can be the only record of. `require_guardian_link` **defaults to True** for the same reason `IsAuthenticated` is the default permission: a clinical endpoint added later that never thinks about the gate is closed rather than accidentally open. **Two callers opt out, and each is a deadlock the gate would otherwise create.** `GuardianLinkView` (`POST/DELETE /api/auth/guardian/`) is how the child asks for the acceptance in the first place. The three `/api/account/specialist-invitation/` endpoints are the second, and the deadlock there is the mirror image: a specialist can only issue the code a *parent* registers with for a child who is already their patient, and accepting is how a child becomes one — gated, the child could never accept, so the code could never be issued, so the gate would never lift. What accepting while gated grants is *nothing*: every clinical endpoint stays shut, so the reports the specialist may now read are derived from no rows at all. `GUARDIAN_GATE_EXEMPT_REASON` in `core/views.py` carries the argument, including why the alternative (issuing a code for a merely *pending* patient) is worse — it needs no act by the child, so anybody who registered as a specialist could attach a guardian account they control to any minor whose address they know. That the gate is a parameter on a shared helper rather than a permission class over every view is what makes both opt-outs one grep. `/api/auth/me/` and `logout/` stay open as well: the route guard reads `me` to learn *why* it was refused. The refusal is 403 with its own message (`GUARDIAN_GATE_REFUSAL`) rather than the "tylko dla konta pacjenta" one, which would be false here — the account *is* a patient's, it is waiting on somebody else. The condition mirrors `needsGuardianLink` in `src/api/auth.ts` character for character (`is_child` **is True** *and* status not `'accepted'`; a truthiness test would gate an `is_child` NULL row, and keying on `guardian_status` being `null` would have locked out every adult patient). Nothing enforces that the two definitions stay in step — change them together. `test_guardian_gate.py` sweeps every clinical URL from one place, because a gate applied to `/api/diary/` and forgotten on `/api/reports/` is not a gate — `/api/account/profile/` is in that sweep. `POST /api/account/password/` deliberately is **not** gated and is pinned as such: everyone has a password, including the accounts that are not clinical subjects, and a minor waiting on a guardian who has reason to change theirs must not be told to come back once somebody else answers a form.
- **A guardian is told in the app that a child is waiting**, on every screen they have, and that is the answer to what used to be listed here as missing. `UserSerializer.pending_guardian_invitations` carries the count (`guardian.pending_invitation_count`), `HeaderMenu` draws a dot on the closed menu button and the number on the entry that leads to the card, and `waitingLabel` in `utils/children.ts` declines it (both the noun and the verb: "prośby oczekują" against "prośb oczekuje"). Three details are load-bearing. It rides on **`me`** rather than its own endpoint, because a badge on every screen would otherwise be a request on every screen — and the count is a fact about the same `user` row the rest of that payload describes. It is **null, not 0, for every account the question does not apply to**, the same convention as `guardian_status`, and keyed on the *role* so a patient costs no query on the endpoint the frontend hits at every app start; `waitingChildren` in `src/api/auth.ts` is the one place that turns null into "draw nothing", so no screen decides that for itself. And the dot is `aria-hidden` with the sentence in the button's `aria-label`, because colour is not a message. The count can go stale — `me` is not re-read on navigation — so `GuardianInvitations` re-reads the session after an answer and **swallows a failure of that re-read**: the decision itself went through, and a lingering badge points at the card that clears it, which is the harmless direction. What is still missing is any way to reach a guardian who does not open the app: this deployment has no mail and no push.
- **The guardian answers on `/parent`**, above the placeholder, via `components/GuardianInvitations.tsx` — the first and only screen a guardian lands on after login, because a child is blocked until it is answered and a card behind a menu would be one nobody finds. It used to sit on `/modules`, which was where every account landed; it moved with the guardians when they got a view of their own (see the parent view below), and moving it was not optional — leaving it on a screen they can no longer reach would have stranded every child mid-signup. No other account renders it, so none fires the request. A failed load says so rather than drawing nothing: silence would read as "nobody asked" while a child waits on the other side of it. The card carries the child's name and address and nothing clinical — accepting is a decision about a person, not a look at their diary.
- **Still missing:** a guardian cannot *undo* an accepted link, and nothing reaches them **outside** the app — no mail, no push — so an invitation is still only seen by a guardian who logs in. Inside the app it is now visible on every screen they have (see the badge note above).

**The parent view: `/parent` (`pages/ParentHome.tsx`), one screen and a placeholder.** A guardian is not a clinical subject — no `patient` row, so everything behind `_require_patient` answers them 403 — and they were nevertheless being dropped on the patient's module chooser and offered a tile into `/home`, which then failed on a refusal the screen could only word as "coś poszło nie tak". What is on the screen is the invitations card (real, and the reason the screen is not *only* a placeholder) and one large placeholder for the rest of the panel.

- **The placeholder is a normal white card, and the wording is the only thing carrying "not yet".** It used to be a dashed, shadowless outline so a card with nothing behind it could not be mistaken for a feature; on the guardian's one screen that read as a rendering fault rather than as an intention, so it was changed on request. What replaces it is the "W BUDOWIE" badge and the heading — and the fact that the body still promises nothing, which is what `ParentHome.test.tsx` actually pins. **The placeholder deliberately does not say what a guardian will see of the child.** That is undecided and is not a UI question: the diary is health data the child writes about themselves, the reports are written for the treating specialist, and this app's one firm rule in the area runs the other way (a patient cannot cut the specialist off — see `pages/Reports.tsx`). Naming "podgląd dzienniczka dziecka" on a placeholder would answer it in markup, and a client reviewing the screen would reasonably read it as settled. `ParentHome.test.tsx` pins the absence.
- **The redirects live in three guards in `App.tsx` and one helper.** `homeRouteFor(user)` is where "which landing screen does this account have" is decided, used by `GuestOnly`, `/` and `RequireGuardianLink`. `RequireGuardian` guards `/parent` itself. And `RequireAuth` gained **`allowGuardian`, defaulting to false** — the same shape as `require_guardian_link` on `_require_patient` and for the same reason: a patient screen added later that never thinks about the question sends a guardian to their own screen rather than to a refusal. **Exactly one route opts out: `/profile`**, and that is a real exception — identity, the consent register (art. 7(3)) and the password form all work for a guardian, and the one thing on that screen that does not is `GET /api/account/profile/`, which the screen itself only asks for when `hasPatientProfile`.
- **`HeaderMenu` is role-aware** (`GUARDIAN_ITEMS`): the parent screen and the profile, nothing else. It has to agree with the guards above — a menu entry the router immediately undoes is worse than no entry — so change the two together.
- **`GET /api/guardian/children/` is what the panel reads** (`GuardianChildrenView` → `guardian.accepted_children` + `account.build_linked_children`; rendered by `components/GuardianChildren.tsx`). Filtered by `parent=request.user` with no permission class of its own, the same convention as the invitations list, and **accepted links only** — reporting on a child before their guardian answered would be the gate working in one direction.
- **It answers with engagement and never with content, with exactly one exception the client asked for**: entry count, streak, and the date of the last entry, plus `needs_attention`. No mood, no emotions, no stress or energy, no risky-behaviour flag, no report figures, no entry text, no `id_medical`. `CHILD_SUMMARY_FIELDS` in `core/account.py` is the list and carries the argument; `test_guardian_children_api.NothingClinicalTests` sweeps the whole payload for leaks, because the failure mode is somebody adding `avg_mood` here and it looking like an improvement. The exception above it, `CHILD_ATTENTION_FIELD`, is deliberately a *second named constant* rather than a fourth entry in that tuple: the list is still "engagement", and what is in the exception had to be argued for separately. The reason is clinical rather than squeamish — a minor who knows a parent reads their diary writes a different diary, which is the same argument the client made when she refused to let a patient cut the specialist off. **Whether a guardian may ever read the content is still undecided and is not a UI question**; the card says out loud that they are not reading it, so silence cannot imply otherwise. `needs_attention` is the client's one step across that line and was taken knowingly — the marker says *that* a report wants attention, never what is in it.
- The figures come from `diary.count_entries`, `dashboard.streak_days` and `diary.last_entry_date` — the same functions the child's own screens use, so a parent and a child cannot be told different things about one diary.
- **`needs_attention` is the one thing here derived from what the diary says**, and it is worth knowing exactly how far it goes. It is True when the child's **most recent weekly report** flagged `RISKY_DAYS_FOR_ATTENTION` (3) days or more with a risky behaviour; `components/GuardianChildren.tsx` draws an ochre `!` inside the `<h3>`, next to the name, labelled **"Ostatni raport wymaga uwagi"** and nothing else. Five properties are the design. It is a **threshold, not an exact count**, or a five-day week would be quieter than a three-day one — the worst way for an alert to be wrong. It is **risky days rather than `harder_days`**: a flagged day is one the patient described in their own words, while harder days are the two lowest moods of the week, and three hard days out of seven is an ordinary bad week that would make the marker meaningless. It travels as a **boolean** — no count, no dates, no note text, no word naming the reason — so the panel *cannot* start quoting the report without a backend change and a decision to go with it, which is the line `CHILD_ATTENTION_FIELD` exists to hold. It is **False for a locked account**, like the figures and for a stronger reason: deriving it is the processing withdrawal stopped. And the guardian still **cannot open the report** — `/api/reports/` answers them 403 — so the marker points at a document they are told to act on rather than read, which is the shape of the client's decision. It reuses `build_weekly_reports` (one definition of which week is last, shared with the patient's Raporty screen and the specialist's copy) at the cost of deriving every report per child; if that ever needs to be cheaper, the fix is a narrower function both callers use, **never** a second definition of "the last report". `test_guardian_children_api.AttentionTests` covers the threshold in both directions, the older-week case, the week in progress, the locked account and the payload sweep.
- **Nothing else on the backend changed for the panel.** `/api/guardian/invitations/` already served guardians and every other endpoint already refused them.
- **`UserSerializer` carries the consent register**, `data_consent_at` and `services_consent_at` — the columns `0004` added and registration writes. They ride on `/api/auth/me/` rather than on a profile endpoint because they are columns on the same `user` row the rest of that payload comes from, and two endpoints answering for one row is two endpoints free to disagree. Sent as the stored moment rather than a date or a boolean (art. 7(1) again), NULL meaning never granted — which is what lets the profile render "Nieudzielona" as a fact instead of inferring it, and is the state every row `mock_data.sql` seeds is in. `0010` added the other half, `data_consent_withdrawn_at` / `services_consent_withdrawn_at`, and the payload carries the pair plus a computed `active` per consent under **one** `consents` key — the flat `data_consent_at` / `services_consent_at` fields are gone from the wire on purpose; see the consent gate below. `UserSerializer` also carries **`pending_guardian_invitations`** — see the badge note above — and **`is_specialist`** — whether a `specjalist` row exists — which is what `homeRouteFor` in `App.tsx` reads to send a specialist to `/specialist`. Sent rather than inferred from the role for the same reason `_require_specialist` checks the row: `user_role` is a nullable text column seeded by SQL, and an account whose role says 'specjalista' with no row behind it would be routed to a panel that 403s on every request. And **`is_patient`**, which is simply whether a `patient` row exists — `_require_patient`'s first check, sent rather than inferred. The obvious inference is wrong: `is_child` is None *both* for an account with no patient row and for a patient row that never answered the question (nullable column, and `mock_data.sql` predates it being set), so `isChild !== null` in the frontend would have hidden the profile's counters from a patient the backend happily serves. The serializer also **caches the `patient` lookup per user**: `is_child` and `guardian_status` both need it and the second calls the first, so this was three queries on the endpoint the frontend hits at every app start and after every 403.
- **Password strength is checked with the user, not without one.** `check_password_strength(password, user)` in `core/serializers.py` is the single entry point, and it exists because `validate_password(value)` — no second argument — silently disables `UserAttributeSimilarityValidator`: it returns immediately when `user` is None, so a password identical to the account's own e-mail passed registration. Nothing about the call looked wrong, which is why it survived; the only symptom is from outside. Registration therefore runs it from `validate()` rather than from a `validate_password` method, where `attrs` already holds the address and the name, and hands it an **unsaved** `User` (the validator only reads attributes off it). `AUTH_PASSWORD_VALIDATORS` names `user_attributes` explicitly — Django's default list is `username`/`first_name`/`last_name`/`email`, three of which `core.User` does not have, so without it the check would only ever look at the address.
- **`LANGUAGE_CODE = 'pl'`**, so Django's own messages (password validators, DRF's "not authenticated") reach the Polish UI in Polish.
- **Rate limiting** is two independent caps on `login/`, and they answer different attacks. `LoginAccountThrottle` (scope `login_account`, `15/hour`) counts attempts against **one account**, keyed on an HMAC of the address the form submitted — read from the raw body, not from a user that was found, so an address nobody registered costs exactly what a real one does and the counter cannot become the enumeration oracle the login response deliberately is not. This is the cap that bounds password guessing: a botnet gives every attempt its own IP and its own per-IP budget, but they all land on the same account counter. A password that actually matches clears it (`reset()`), or somebody logging in from several devices in an hour would lock themselves out. It is **silent until `WARN_AT_ATTEMPTS_LEFT` (5) remain** — i.e. from the 10th failure — then folds "Pozostało N prób…" into `detail`, counting down to "To była ostatnia próba…" on the 15th; announcing the budget earlier would only tell an attacker how much room they have. Folded into `detail` as one string because `firstMessage` in `src/api/client.ts` renders a list's first entry and drops the rest. `ReportPdfThrottle` (`report_pdf`, `30/hour` per account) is a capacity cap rather than a security one — see the reports section. `PasswordChangeThrottle` (`password_change`, `10/hour` per account) is a security one again: `POST /api/account/password/` verifies the *current* password, so it is a second oracle for guessing it, reachable from a session left open on a borrowed phone — and the login cap counts nothing there, since a signed-in caller submits no address. Its own scope rather than the shared `'auth'` one, so that changing the login limit does not silently change this; `GuardianLinkThrottle` still shares `'auth'`, which is a wart worth fixing the same way. `SpecialistInviteThrottle` (`specialist_invite`, `60/hour` per account) bounds the two forms where a specialist names somebody by e-mail, and it is what makes their deliberately uninformative refusals worth having — "refused" versus "accepted" is itself an answer, so it has to be a bounded question. It is applied **on POST only** (`get_throttles` on both views): the panel reads its caseload on every screen it has, so counting those reads would lock a specialist out of their own list by the middle of a working day in exchange for bounding a request that reveals nothing. `SpecialistAccountThrottle` (`specialist_account`, `20/hour` per account, POST only for the same reason) bounds `POST /api/specialist/colleagues/`, and it is a different kind of cap again: what it limits is not an enumeration oracle but a session used to *mint professional accounts*. Its own scope so that changing what bounds the invitation forms does not quietly change what bounds account creation. The per-IP cap on `login/`/`register/` is `10/min` (and `10/min` per account on `auth/guardian/`, via `GuardianLinkThrottle`, a `UserRateThrottle` — `AnonRateThrottle` exempts requests carrying a session, so the per-IP cap would have counted nothing there), counted in `CACHES['default']`, which is Django's `DatabaseCache` on a `throttle_cache` table in `user_db` (`core/routers.py` sends the non-`core` app label to `default` on its own). It used to be the default local-memory cache — per *process*, so every cap was worth as much as the number of gunicorn workers and the login limit bounded nothing in particular, since which worker answers is the load balancer's choice. There is no Redis in this deployment and a handful of counters does not justify adding one to run and pay for. Two details are load-bearing: the table is created by `0008_throttle_cache_table` rather than by a documented `createcachetable` step, because a missing table makes every cache write raise and DRF reads an unreachable cache as "no history" — i.e. the caps **fail open**; and `OPTIONS['MAX_ENTRIES']` is `20000` rather than Django's default `300`, because `DatabaseCache` culls once past it and a culled row is a counter back at zero, i.e. the cap failing open under exactly the load that caused the culling. `test_migrations.ThrottleCacheTableTests`/`ThrottleCacheSettingsTests` pin both, plus the fact that the migration's table name and the setting still agree. Both classes live in `core/throttling.py` and mix in `HashedIdent`, so the **cache key holds an HMAC-SHA256 of the caller's address rather than the address** — DRF writes that value straight into the key, and now that the cache *is* a table in `user_db` that is the difference between a counter and a log of client IPs sitting next to the PII — `HashedIdent` was written against exactly this move. Keyed on `SECRET_KEY` rather than a bare digest, since IPv4 is 2**32 values and an unkeyed hash of one pseudonymizes nothing. `NUM_PROXIES` is `1`: unset, DRF keys on the *whole* `X-Forwarded-For`, which the client writes, so a different value per request bought a fresh budget and the cap counted nothing. One trusted hop means the last entry is the address App Service actually saw; raise it if a proxy is added, and never set it to `0` behind one, which would put every client on the internet on a single counter.

**The specialist view: `/specialist` (`pages/SpecialistHome.tsx`), four things and a stated limit.** A specialist is not a clinical subject either — a `specjalist` row and no `patient` row, so everything behind `_require_patient` answers them 403 — and like guardians before `/parent` existed they were being dropped on the patient's module chooser. The panel has the caseload (with a link into each patient's weekly reports), a link to the guardian-code screen, one to the screen that creates another specialist's account, and one to the technique editor.

- **Being a specialist authorizes nothing by itself, and that sentence is the whole security model here.** `_require_specialist` (`core/views.py`) is a routing decision, not access control: what puts a patient's reports in front of somebody is that patient accepting an invitation. `assigned_patient` re-checks that per request, on every URL carrying a patient id. Do not add anything that writes `patient.id_specjalist` directly. Note that this did **not** change when specialist accounts stopped being self-service: raising the bar on getting a `specjalist` row is worth having, but nothing here leans on it, and a design that did would be one bad account away from every patient's reports.
- **The assignment is an invitation, mirroring the guardian one.** `POST /api/specialist/patients/` (the specialist) names a patient by e-mail and sets `id_specjalist_pending`; the patient answers on their own home screen via `GET/POST /api/account/specialist-invitation/{,accept/,reject/}`. Accepting moves the id into `id_specjalist` and stamps `specjalist_accepted_at`; refusing clears the pending column and **records nothing**, which is the same choice `parent_child` makes for a refused invitation (0007) — a stored "no" would be a state neither side can act on, while an absent one lets the specialist ask again after talking to them. The rules live in `core/specialist.py`, out of the views like `core/guardian.py`.
- **The patient cannot end an accepted link; the specialist can** (`DELETE /api/specialist/patients/<id>/`). That is the client's rule, not an omission: with eating disorders the tendency to hide information rises, so a patient-side switch would disable the reports exactly in the cases they exist for — the same decision as the TODO in `pages/Reports.tsx`, which has already survived one attempt to turn it into an opt-in. `components/SpecialistInvitation.tsx` says so **before** the tap, because a consent given without that sentence is not informed.
- **The patient's card lives on two screens, and the second one is load-bearing.** `components/SpecialistInvitation.tsx` sits on `/home` and on **`/link-guardian`**, because `RequireAuth` redirects an unlinked minor away from `/home` — so with the card on `/home` alone the API exemption above was an exemption in name only: the specialist saw "oczekujące" and the child had no button to press. A gated minor answers on the one screen they can reach.
- **The invitation form answers one thing however it fails, with one exception.** A patient who is *already this specialist's* is told so by name (`ALREADY_MINE`): they are visible in the list above the form, so saying it leaks nothing, while the shared message told the specialist "nie znaleziono" about somebody they were looking at. Everything else — unknown address, a guardian's, a colleague's, somebody else's patient, one another specialist is already asking — keeps the single refusal.
- **The invitation form answers one thing however it fails.** An address nobody registered, a guardian's, another specialist's, a patient who already has a specialist and one somebody else is already asking all get the same refusal (`SpecialistPatientInviteSerializer`) — otherwise the form is a way to ask who has an account here and what kind of care they are in, which for a mental-health service is itself sensitive. The specialist's own address is the one exception, answered specifically, mirroring `OWN_ADDRESS` on the guardian form. `SpecialistInviteThrottle` (`specialist_invite`, `60/hour` per account) is what keeps the shared refusal worth having: "refused" versus "accepted" is itself an answer, so the asking has to be bounded.
- **Ending care asks twice** (`components/SpecialistPatients.tsx`), like deleting a technique and for a heavier reason: the patient cannot undo it or restore it — they would have to be invited again and accept again — so a stray tap on a phone would end a care relationship and drop the reports it exists for. Withdrawing a *pending* invitation is one tap, because it takes nothing away.
- **The caseload payload is engagement, never content** — `PATIENT_SUMMARY_FIELDS` in `core/specialist.py`: name, address, `is_child`, when they accepted, and the same entry-count/streak/last-entry figures the parent panel and the patient's own profile show (the same functions, so a specialist and a patient cannot be told different things about one diary). No mood, no emotions, no flags, and **no `id_medical`** — the row id on the wire is the patient's `user` id. The clinical content is one screen further in, in the reports, which is a document you open deliberately rather than a figure in a list of nine patients. `test_specialist_api.CaseloadPayloadTests` sweeps the payload for leaks.
- **Two lists, never one.** Accepted and pending are separate keys, so a screen cannot render a pending patient as a treated one by forgetting to read a status field — and a pending row carries `activity: null`.
- **The reports a specialist reads are the same documents the patient sees**, built by the same `build_weekly_reports` from the same rows: `GET /api/specialist/patients/<id>/reports/{,<week-id>/,<week-id>/pdf/}`. `components/ReportSections.tsx` was extracted from `pages/ReportDetail.tsx` so the *body* of a report has one definition too — the two people in the consulting room must not be holding different papers. The frame differs (where "back" leads, and a note written for a reader who did not write the entries), and **the flagged days are not links on the specialist's copy**: their access is the reports and nothing else, so a link into the diary entry behind a flagged day would answer in markup a question that is still open with the client. `ReportPdfBase` is the shared half of the two PDF endpoints; the document carries the **patient's** address on both, because a printout has to say whose week it is.
- **A patient who is not this specialist's answers 404 on every id-carrying URL**, not 403 — a 403 would confirm the account exists and is a patient, exactly what the invitation form takes care not to answer. Same convention as `/api/diary/<id>/`.
- **Guardian accounts a specialist starts: `parent_invitation` + `/api/specialist/parent-invitations/`.** The guardian link is normally started by the child; a specialist sitting with a family needs the other direction, and **this deployment sends no mail at all**, so the invitation travels as a code handed over in the room. Three properties matter: the code is **stored hashed** (`make_password`, like `user.password_hash`) and the plaintext exists only in the response that created it — a specialist who loses it revokes and re-issues, and no endpoint can read it back; it is **bound to one address**, so the parent has to register with the address the specialist named; and it **expires** (`INVITATION_TTL_DAYS`, 14). `CODE_ALPHABET` leaves out every character that is read wrong off a handwritten card (O/0, I/1/L, S/5, Z/2) because this code is dictated and typed by hand. **The child has to be the specialist's patient already**, which is why the specialist-invitation endpoints are exempt from the guardian gate — see the note in the authentication section; without that exemption the whole flow deadlocks for exactly the children it exists for. `test_parent_invitation_api.DeadlockTests` walks it end to end, from a blocked minor to an unblocked account. Redeeming happens inside the registration transaction (`RegisterSerializer._redeem`), so a password the validators refuse cannot burn a code, and it creates the `parent_child` row **already accepted** — the one place this differs from the child-initiated flow, and not a hole in the art. 8 gate: the guardian accepts *by completing the registration* with a code handed to them in person, and what the specialist contributes is the one fact the app cannot check itself, that these two people are a family. A used invitation is marked, never deleted: the account it created exists, and dropping the row would only lose the trail. **This is now the only way a guardian account comes into existence** — see `ACCOUNT_TYPES` above; it used to be one of two, the other being a guardian registering on their own and being named by the child afterwards.
- **Specialist accounts a specialist creates: `/api/specialist/colleagues/` (`core/colleagues.py`, `pages/SpecialistColleagues.tsx`).** This is now the **only** way a specialist account comes into existence — the registration form has no such account type and `ACCOUNT_TYPES` maps none, so a hand-made `account_type: 'specialist'` is a 400. The reason for the move is not access (the role grants nothing, as above) but the claim: a professional account asserts a qualification the app cannot check and a colleague can. Four properties matter:
  - **The password is generated, returned once, and stored hashed** (`make_password`, like `user.password_hash`) — the same shape as a guardian invitation code and for the same reason: this deployment sends no mail at all, so a credential travels as something handed over in the room. Nothing can read it back, and there is no password reset here either, so an account whose password is lost has to be created again on another address. `PASSWORD_ALPHABET` is imported from `parent_invitations.CODE_ALPHABET` rather than copied — it is dictated and typed by hand, so O/0, I/1/L, S/5 and Z/2 are a support call rather than a typo. **And it has to be replaced at first login** — see the password gate below: the account holds a credential its owner did not choose and its creator knows, and what the panel opens onto is other people's records.
  - **The new account grants no consents, and that is the load-bearing half.** Registration writes `data_consent_at`/`services_consent_at` because the person ticking the boxes *is* the person consenting; here they are not, and RODO art. 7 makes consent the data subject's own act. So both columns stay NULL, `HasActiveConsents` refuses the account everything, and its owner grants them at first login on `pages/ConsentsRequired.tsx` — which also means the account cannot read anything before its holder has agreed to anything. `test_specialist_accounts.NewAccountTests` walks that from creation to an open (and empty) panel.
  - **Nothing in the app can create the first one, by construction**: creating a specialist account needs a `specjalist` row, and the only way to get one is from a `specjalist` row. `scripts/mock_data.sql` is the bootstrap — `anna.kowalska@example.com` / `Haslo123!`, given a real hash and both consents by an `UPDATE` next to the demo patient's row, precisely because the seed would otherwise leave the panel unreachable. On a real deployment it is the same act: one row by hand, then every further account from inside the app. That property is worth keeping rather than closing: an endpoint that could mint the first professional account could mint the tenth.
  - **The roster is every specialist account, and it carries professional identity only** — `COLLEAGUE_SUMMARY_FIELDS`: name, address, specialization, when it was created, and whether its consents are in force. **No caseload and no counters of any kind**: a colleague's patients agreed to *them*, and a list of colleagues is exactly where somebody would add a patient count thinking it an improvement (`RosterTests.test_nothing_clinical_and_no_caseload_travels` is the sweep). It is not filtered to the accounts you created — there is no column recording that, and the roster's actual job is to stop a second account being made for somebody who already has one, which the form can otherwise only answer with "ten adres jest już zajęty". `consents_active` travels so the screen can say "waiting for its owner" rather than showing a row that reads as broken.
  - There is **no delete and no edit** (405 on both). Closing an account is the same unanswered legal question as deleting a patient's, and it is not answered differently for a specialist.
- **Writing a technique: `/api/specialist/techniques/` and `GET /api/techniques/`.** See the catalogue section below — the short version is that a technique a specialist saves is a catalogue entry like any other, visible to every patient the moment it is saved (there is no draft state), and `author_id_specjalist` gates who may **edit** it rather than who may read it.
- **What the panel deliberately does not have**, and the screen says so in words (`.specialist-scope`) rather than promising it later: no view of a patient's diary and no analysis screens. Whether a treating specialist may read the diary itself is open with the client, the app's one firm rule in the area runs the other way (a patient cannot cut the specialist off), and naming it on a placeholder would let a client reading the screen take it as settled — the same reasoning as `ParentHome`'s placeholder.
- **One specialist per patient**, because `patient.id_specjalist` is a single FK. That is a real limitation rather than a decision: the app has two modules (psychotherapy and psychodietetics) and the client's visibility rule speaks of "the specialists treating the patient" in the plural, so a patient seeing both a psychotherapist and a dietitian cannot be expressed today. Making it many-to-many is a new table plus a rewrite of the profile's care card, and it is the first thing to do here if the client confirms the plural.
- **The redirects are four guards in `App.tsx` and one helper.** `homeRouteFor` now answers specialist → `/specialist`, guardian → `/parent`, everyone else → `/modules`; `RequireSpecialist` guards the panel; and `RequireAuth` gained **`allowSpecialist`, defaulting to false**, the same shape and reason as `allowGuardian`. Two routes opt in: `/profile` (identity, consents and the password form are genuinely theirs) and **the technique catalogue**, because a specialist writes into it and seeing what a patient sees is the point. `HeaderMenu`'s `SPECIALIST_ITEMS` has to agree with those guards — change them together; `/specialist/colleagues` is in both.

**The profile's own endpoints: `/api/account/`.** Two, and the split between them is which database they need:

- **`GET /api/account/profile/`** answers with the two counters and the care card — everything on "Profil" that is neither identity nor consent. `core/account.py` is the aggregation, and it is **the one module in the project that reads both databases**: the counters come from medical_db through `id_medical`, the specialist from user_db through `patient.specjalist`. That meeting point is deliberately in one named place, so `core/dashboard.py`, `core/reports.py` and `core/frequency.py` can go on seeing nothing but a UUID. Behind `_require_patient`, so a guardian is refused rather than told they have written 0 entries and have no therapist — both true of a row that does not exist, and both reading as a clinical record. `hasPatientProfile` in `src/api/auth.ts` mirrors that rule so the frontend does not make the request at all; the refusal is there because a route guard is not enforcement.
  - **Neither counter is computed here.** `entry_count` is `diary.count_entries` and `streak_days` is `dashboard.streak_days` — the same functions behind `GET /api/diary/` and `GET /api/dashboard/home/`, which is why the latter is public rather than `_streak_days`. The profile is a summary of screens the patient can open, and a summary that disagrees with the screen it summarises is worse than none. `count_entries` is deliberately not capped at `MAX_HISTORY_ENTRIES`: that cap bounds a list, and a `COUNT(*)` has no such problem.
  - **`care` is nullable and so is its `approach`.** `patient.specjalist` is SET_NULL and an account registered before the first appointment has nobody assigned — an ordinary state the screen says in words. `approach` maps onto `specjalist.specjalization`, the closest thing the schema holds; treat a difference from the mockup's "nurt" as a schema question, not a mapping bug. **`phone` is always null**: no table holds a specialist's number, and `api/profile.ts` drops anything arriving under that key rather than trusting it — the safety plan renders a `tel:` link off it, and a live link that fails when tapped reads, in a bad moment, as the therapist's number being out of service. Where that number should live is a decision for the specialist panel.
- **`POST /api/account/password/`** changes the signed-in account's password and answers 204 with no body. The current password is re-asked and checked **server-side**: a live session proves the device, not the person holding it. It is validated for *presence only* — rows seeded by `mock_data.sql` and accounts created before the 8-character rule hold passwords today's validators would reject, and running them through would put "min. 8 znaków" under *Obecne hasło* and leave those accounts unable to submit the form at all. `src/components/ProfilePasswordForm.tsx` makes the same call for the same reason. The new password goes through `check_password_strength` with the user, so it can be refused for resembling the account's own address or name. **Other sessions survive**: ours carry `core_user_id` and no password hash, so nothing goes stale — signing an account's other devices out is a real feature, but it needs a way to enumerate its sessions, which this deployment has not got.
- **`POST /api/account/consents/withdraw/` and `.../restore/`** are the consent gate's two ends — see below.
- **Still stubs, each blocked on a decision rather than on effort** (`src/api/account.ts`, which rejects instead of faking success): account deletion needs the legal question about retaining clinical records answered first; the e-mail change is two endpoints, not one, because a new address has to be confirmed from a message sent *to it* and there is no mail out of this deployment; and data export (art. 15/20) is still owed after being removed from the screen.

**The consent gate: without both RODO consents, the app answers one screen.** `core/consents.py` holds the rule, `core/permissions.py` enforces it, `pages/ConsentsRequired.tsx` is the screen.

- **Withdrawing locks the account; it does not delete it.** The older reading — the app processes health data and nothing else, so losing the art. 9 consent ends the account — got the premise right and the conclusion wrong. Stopping the processing does not require destroying the record, and equating the two made exercising a right (art. 7(3)) irreversible an hour later when somebody changed their mind. Nothing is removed: the diary sits where it was and comes back unchanged when the consent does. **Deleting the account stays a separate, still-stubbed decision**, which is where irreversibility belongs. This also settles the `TODO(klientka)` on the services consent: the app *is* a service of the foundation, so both consents are required and neither is the milder one.
- **Withdrawal is its own column, not a cleared grant.** `0010` adds `data_consent_withdrawn_at` / `services_consent_withdrawn_at` to `"user"` (user_db, so the `RunSQL` carries `hints={'target_db': 'default'}`; `database_setup.sql` mirrors them). A consent is active when `granted_at is not None and (withdrawn_at is None or withdrawn_at <= granted_at)` — **written once, in `consents.is_active`**, because the permission class, the serializer and both endpoints all have to agree. Restoring writes a fresh `granted_at`, later than the withdrawal, which turns the comparison back on without erasing either event. That keeps the last cycle per consent, not a full audit log; a table is the answer if one is ever needed.
- **THE GATE APPLIES TO THE SUBJECT OF THE DATA, NOT ONLY TO THE READER OF IT.** `HasActiveConsents` gates the account *making* a request, which was every reader this app had while a patient could only read their own diary. The parent panel and then the specialist panel introduced second readers, and the gate did not follow them: a patient could withdraw both consents, watch their own diary answer 403, and have their **full weekly report — risky-behaviour note included — served to their specialist anyway**, while a guardian went on being shown a locked child's entry count and streak. Both are closed by asking the same `has_active_consents` about the *patient*: `specialist.patient_locked` (403 with its own message on all three report URLs, checked in `_assigned_patient`, the one funnel they share) and `account.build_linked_children` (no figures at all). Neither hides the person from the list — the specialist and the guardian are told the account is locked, because that is a fact about an account rather than about anybody's health, and silence would read as "stopped writing". `consents_active` travels for exactly that reason: the card that used to say "to konto nie prowadzi dzienniczka" would otherwise be describing an account that has a diary and has stopped it. Anything that adds a third reader of somebody else's clinical data has to make the same call — `test_specialist_api.WithdrawnConsentTests` and `test_guardian_children_api.WithdrawnConsentTests` are the two sweeps to copy.
- **The gate is a default permission, not a shared helper.** The guardian gate lives inside `_require_patient` because every clinical endpoint already calls it; this one applies to *everything*, including endpoints that touch no patient row, so it goes in `DEFAULT_PERMISSION_CLASSES` next to `IsAuthenticated`. **The trap is that setting `permission_classes` on a view replaces the defaults wholesale**, so every exemption uses the named `CONSENT_EXEMPT` rather than spelling `[IsAuthenticated]` out — the exempt set is one grep, and `test_consent_gate.py` sweeps every registered URL to prove nothing else slipped out. Exactly four are exempt, each the gate's own escape hatch: `me/` (how the frontend learns *why* it was refused), `logout/`, and the two consent endpoints.
- **Both consents, not either**, and an account that never granted one is treated exactly like one that withdrew it — rows seeded by `mock_data.sql` have neither column set and belong on the same screen. `needsConsents` in `src/api/auth.ts` mirrors `has_active_consents` character for character; change them together. It **fails open** on a payload with no `consents` block, unlike `needsGuardianLink`, and deliberately: a deployed backend a release behind would otherwise black out every client, and the server refuses on its own regardless.
- **Restoring asks for no password.** It is the direction that *unblocks* an account, so friction costs somebody who changed their mind and protects nobody — whoever reaches the endpoint is already inside the session. Withdrawal keeps its password prompt.
- **The screen offers signing out at the same weight as restoring**, on purpose: a screen where restoring is the only escape is pressuring somebody into a consent, and a consent given under pressure is not one (art. 7(4)).
- **`AccountClosureConfirm` now shows two different lists** — "Co zostanie usunięte" for deletion, "Co się stanie" for a withdrawal that removes nothing. Reusing the first over a reversible act was a false statement on the one screen whose job is to be precise about consequences.
- **`active` travels on the wire and is never recomputed in the browser**, and that rule was bought with a bug. `consents` is a `SerializerMethodField`, whose return value the JSON encoder wrote as UTC with a `Z`, while the declared `data_consent_at` field went through DRF's `DateTimeField` and came out in `settings.TIME_ZONE` with `+02:00` — the same instant, twice, in two formats. `ConsentsRequired` compared them as **strings** to decide whether a consent still held, and `'…T10:…Z' <= '…T12:…+02:00'` is true, so a consent withdrawn a fraction of a second after it was granted read as active: the screen showed "Udzielona", rendered no restore button, and left the account with nothing but the logout link. Both halves are fixed — the method field renders through `serializers.DateTimeField` so one instant has one representation, and the duplicate top-level fields are gone so there is nothing to compare against — but the durable fix is that `core/consents.is_active` is the only place that comparison exists. `consentGrants` in `utils/consents.ts` keys on `active` for the same reason: `granted_at` survives a withdrawal (art. 7(1)), so keying on its presence listed a withdrawn consent as "Udzielona". `test_consent_gate.PayloadConsistencyTests` pins the rendering, and `ConsentsRequired.test.tsx` pins that a payload whose dates sort the wrong way as text still offers the consents back.
- **Withdrawal keeps the session.** The account still exists and its owner has to reach the screen offering the consents back; signing them out would put it behind a login they may not want to perform. Only deletion ends the session.

**The password gate: an account holding a password somebody else generated reaches one form.** `core/permissions.py` (`HasOwnPassword`, next to `HasActiveConsents` in `DEFAULT_PERMISSION_CLASSES`), `user.must_change_password`, and `pages/PasswordChangeRequired.tsx`.

- **One kind of account carries it**, and `core/colleagues.py` is the only thing that sets it: a specialist account created by a colleague. That password is *generated* — it comes back once in the creating response, is read off a note and typed by hand — so its holder did not choose it and at least one other person knows it, which is true of no other credential in the app. Being signed in is therefore not yet evidence of who is at the keyboard, and what the panel opens onto is other people's weekly reports.
- **The consents come first, and that order is forced rather than preferred.** `POST /api/account/password/` is itself behind `HasActiveConsents`, so an account sent to the password screen with its consents missing would find the one form it may use answering 403. `gateRouteFor` in `App.tsx` writes the order down once for all six route guards; `test_password_gate.OrderTests` pins it on the API.
- **The exempt sets are two named constants, not two spelled-out lists.** `CONSENT_EXEMPT` opts out of *both* gates (`me/`, `logout/`, the two consent endpoints) and `PASSWORD_CHANGE_EXEMPT` is `[IsAuthenticated, HasActiveConsents]` — used by exactly one view, the way out. Same trap as the consent gate: setting `permission_classes` replaces the defaults wholesale, so `test_password_gate.SweepTests` sweeps every registered URL from one place.
- **The flag is cleared where the hash is written**, in `PasswordChangeSerializer.save`, unconditionally and in the same `update_fields`. A branch would be a second place for the two to disagree, and saving them apart would leave an account either keeping a screen it has left or leaving one it has not.
- **The screen renders the profile's own `ProfilePasswordForm`**, with three props' worth of difference: it calls the first field "Hasło otrzymane przy zakładaniu konta" (nobody chose it, so "obecne" would describe a decision), it re-reads `/api/auth/me/` afterwards and hands the result to the session (the endpoint answers 204 with no body, so unlike the consent screen there is no updated user to take from the response), and the route guard — not the component — moves the app. A second copy of the form would be a second set of rules about what a password may be.
- **Signing out sits below the form.** The same argument as on the consent screen, in a weaker form: somebody whose note is at home must be able to leave rather than be held on a form they cannot fill in.
- **`needsPasswordChange` in `src/api/auth.ts` fails open** on a payload with no `must_change_password`, like `needsConsents` and unlike `needsGuardianLink`: no backend without the column has an account the flag could be true for, and the server refuses on its own regardless.

**The diary's own endpoints: `/api/diary/`.** `core/views.py` exposes three, and the split between them *is* the product rule — one entry per calendar day, editable on the day it was written, everything older read-only:

- `GET`/`PUT /api/diary/today/` — the only writable one, and it can only ever address today. `core/diary.py` `save_today_entry` replaces rather than merges: the form submits its whole state, so a field left out is an answer taken back, not one left unchanged.
- `GET /api/diary/` — the archive, newest first, today included. Read-only structurally rather than by permission: there is no write verb on the URL.
- `GET /api/diary/<uuid>/` — one past entry. The **only** diary URL carrying an id, and therefore the only one where a caller can name a row that is not theirs; `load_entry` filters on the session's `id_medical` alongside the id, so somebody else's entry answers exactly like a nonexistent one (404, nothing leaked about whether it exists). Route order matters: `diary/today/` is declared before `diary/<uuid>/`.

**An untouched slider is not an answer, and an untouched *chip* has nowhere to say so.** `emptyDraft` in `pages/DiaryEntry.tsx` used to start `energyLevel`/`tensionLevel` at **0**, so an entry that answered the mood tile and one emotion — the whole form, as far as the patient was concerned — was written as *no* energy and *no* tension. It was not theoretical: saving one such entry dropped "Średnia energia" on `/home` from 5,0 to 2,5, and the same columns feed the weekly report a therapist reads. Both now start at **null**, which is what `core/diary.py` documented all along ("NULL — which is not the same as a slider deliberately left at 0"). The sliders still render at 0 (`draft.energyLevel ?? 0`); what changed is that not touching one no longer answers it — and the edge that leaves behind is that a *deliberate* 0 takes moving the slider off and back, which `DiaryEntry.test.tsx` pins rather than hides. **Emotion intensity is the deliberate exception**: `mood_scale` keeps one nullable column per emotion and NULL there already means *the chip was never picked* (`_read_ratings` skips NULLs, which is what redraws the chips as the patient left them), so a picked-but-unrated chip stored as null would simply vanish the next time the entry is opened. It therefore still travels as 0, at a real cost — it reads as "wcale" and pulls that emotion's weekly average down, which is what put 'Smutek' at 0,8/10 over five days in the week that settled how the ranking is drawn. Recording "picked, unrated" honestly needs somewhere to keep the picked-set, i.e. a schema change; it is worth settling before the diet module's four 0-10 sliders (§05 of its mockups) repeat the same question.

`serialize_entry` is shared by all three and carries `id` plus `saved_at` (`updated_at`, i.e. when it was last saved) on top of what the form edits — the archive needs both. `MAX_HISTORY_ENTRIES` is a runaway-query backstop, not a product limit; hitting it means the screen needs real pagination.

**The home screen's data: `GET /api/dashboard/home/`.** `core/views.py` `HomeDashboardView` answers with everything `frontend/src/pages/Home.tsx` draws — streak, today's entry, the 7-day chart, the stress/energy averages — plus `technique`, which nothing draws any more (see below). The aggregation itself is in `core/dashboard.py`, kept out of the view so it can be tested (and reused by the analysis/report screens) without a request.

- **The session is the only identity input.** The view resolves `request.user` → `Patient.id_medical` (user_db) and passes that UUID to `build_home_dashboard`, which touches nothing but medical_db. There is no patient id in the URL, so one account cannot ask for another's numbers, and the aggregation code never sees a name or an e-mail.
- **An account with no `patient` row is refused, not answered with zeroes** — a guardian or a specialist is not a clinical subject, so an empty diary would be a misleading answer rather than a true one. Guardians get to a child's data through the parent panel, which does not exist yet (`parent_child` is still unwritten — see the note above).
- **`core/emotions.py` is the shared vocabulary**, and `frontend/src/utils/emotions.ts` holds the same ten names plus a colour for each. The strings have to match character for character: the API sends names and the chart looks up colours by them. Nothing enforces that — `api/dashboard.ts` treats a name it does not recognise as "no colour" rather than drawing an invisible bar.
- **One of the ten emotions has no scale column.** `mood_scale` covers nine (`shame_scale`/`calm_scale` were added by `0005`) and `diary.stress_level` supplies 'Stres'. A day can still legitimately have a named emotion and no intensity — rows written before `0005`, or an emotion named in `diary.current_strongest_emotion` that was never rated — which the chart draws as a fixed-height bar in that emotion's colour.
- **`current_strongest_emotion` wins over the sliders** when `normalize_emotion` can read it, with its height taken from the matching slider. Unmappable text — the seed data alone contains 'zmęczenie' — falls back to the highest rating instead of being forced into the nearest name. The column was designed to hold the patient's own answer to "what did you feel most strongly", but the entry form never asks that question, so `core/diary.py` derives it from the highest rating on save (`strongest_emotion`, sharing `dashboard._ratings`' tie-break order so the two can never disagree). Rows written before that, and the seed data, are the only ones where the column means anything else. If the form ever grows the question, that is the line that should start trusting the answer instead.
- **The technique suggestion is read from `raport`, not computed here** — whatever produces the reports is where that judgement belongs, and a second opinion invented on the dashboard would quietly disagree with the one in the reports screen. **The card that rendered it ("Propozycja na dziś") was removed from `/home` on request**, and the endpoint keeps sending the field. Removing the card rather than the field is deliberate: the suggestion was unreachable in practice and misleading when it did appear — nothing writes `raport`, so the only names it could carry were the three `mock_data.sql` seeds ('Body scan', 'Dziennik emocji', 'Technika 5-4-3-2-1'), none of which is in the catalogue the card linked to, so tapping a named technique landed on a list of eleven other ones. That contradiction was the `TODO` the card carried. `api/dashboard.ts` therefore does not declare `technique` on its payload type and maps nothing from it, `types/dashboard.ts` no longer has a `TechniqueSuggestion`, and `api/dashboard.test.ts` pins that the field is dropped rather than carried into the screen's shape. Putting the card back is one field, one mapping and the component from git history — but the thing that has to change first is that `raport` should reference a technique by **id** rather than by name, or the same broken link comes back with it.
- **`settings.TIME_ZONE` is `Europe/Warsaw`** (rows are still stored in UTC). It decides which calendar day a `created_at` belongs to, so under UTC an entry written at 00:30 would have counted towards the previous day.

**The "Raporty" screens are derived, not stored.** `frontend/src/pages/Reports.tsx` (the history) and `pages/ReportDetail.tsx` (one report) draw what `GET /api/reports/` answers — see the reports section below for how it is built. Derived on every request from the same rows `/api/diary/` returns, so no number on a report can disagree with the entries it came from; `raport` in medical_db is **still unwritten by anything**, which is a separate gap from the endpoint existing (see "Still to do" below).

The rules that shape those screens came from the client and are not free choices:

- **Reports are generated automatically, once a week**, from diaries and nothing else (confirmed twice). The patient does not create one and does not pick a range, so there is no generator UI and no Tydzień/Miesiąc/Kwartał switch — the mockup's pages 9-10 predate that decision. A quarterly report is an open question with the client; a daily one was rejected outright as a copy of the diary. `buildWeeklyReports` therefore skips the week in progress (a report exists once its week has ended) and any week with no entries at all (nothing to report on) — the latter also counts as "no previous week" for the week after it, so its deltas read as *brak poprzedniego tygodnia* rather than as a drop to zero.
- **Reports are visible to the specialists treating the patient, and only to them; the patient cannot cut that off.** Dropping a link is the specialist's action. The client's clinical reason: with eating disorders the tendency to hide information rises, so a patient-side switch would disable the feature exactly in the cases it exists for. This was contested earlier in the project, so `Reports.tsx` carries a TODO saying so — do not turn it back into an opt-in share step. Hence no "Wyślij terapeucie" button anywhere, only a plain informational note. "Pobierz PDF" stays, because saving a file to your own device is not an act of sharing; it is implemented (`GET /api/reports/<week-id>/pdf/`).
- **Changes are always a direction and a value** ("+0,6 od poprzedniego tygodnia", "Lęk −4 dni"), never an assessment of the patient, and an unfavourable move is ochre rather than the error red. Which direction is favourable is only asserted for the four metrics plus tension, because the app already asserts it elsewhere (the mood scale is ordered, "trudniejsze dni" says so in its name, and the sliders are labelled *wyczerpanie ↔ pełnia energii* / *rozluźnienie ↔ skrajne napięcie*). Emotion chips are deliberately untoned: whether more days of 'Lęk' is bad is a clinical judgement this screen is not entitled to make — see `tone()` in `utils/reports.ts`.
- **Risky behaviour reaches the reports** (the client asked for it; it is not in the mockup). Its section is rendered even when the week held none, because "none this week" is itself a reading for a specialist and a section that appeared only on bad weeks would announce them from the table of contents. Styling is the entry form's ochre, never red.
- **Two mockup sections are deliberately missing**, each with a TODO where it belongs: "Skuteczność technik" needs a way to rate a technique after applying it, and "Realizacja celów" needs the therapeutic-goals system. Both are extension-priority and neither exists, and a percentage computed from nothing would be a made-up number in a document a therapist reads.
- **A missing comparison is two different answers.** `Delta.gap` says which: `'no-previous-week'` is genuinely the first week, `'unrated'` is a week that exists and never answered that question (every field on the entry form is optional, so a patient can log seven days and skip the mood tiles throughout). They get different wording, in the cards and in the summary sentence, because "there is no previous week" is a false statement about a week that has entries in it — and it would be false inside a document a therapist reads.
- **The week-has-ended cutoff is read in `settings.TIME_ZONE`**, the same clock `core/days.py` uses to decide which calendar day an entry belongs to. It used to be read from the browser, which made a report appear a few hours late west of Warsaw; moving the aggregation to the backend is what fixed it.
- The narrative summary is composed from the same figures the cards show (`buildSummary`) rather than hard-coded, but it is still a placeholder: the real one belongs where the report is generated, next to the technique suggestion the dashboard still reads out of `raport` (and no longer shows).

`src/utils/days.ts` and `placeLabel` in `src/utils/triggers.ts` were extracted while building this: `toIsoDate` had been copied into `Journals.tsx` and `DiaryEntry.tsx`, and the chip/"Inne" unpacking into `Journals.tsx` and `JournalDetail.tsx`. Both now have one definition, which is what lets a report count places the same way the diary displays them.

**Weekly reports: `/api/reports/`.** Two rules worth knowing before touching the numbers: `_round1` uses `Decimal`/`ROUND_HALF_UP`, not `round()`, whose banker's rounding sends 0.25 to 0.2 while sending 3.35 to 3.4 depending on where the float lands — unpredictable at the boundary is a poor property for a figure read clinically. And `_polish_key` compares `(base letter, diacritic rank)` pairs rather than appending a marker to the base letter: with 'ł' rendered as 'l' plus a low marker, the marker also sorts below every real letter and "Łódź" comes out before "Lublin". `core/reports.py` turns diary entries into one report per completed Monday–Sunday week; `core/report_pdf.py` renders the same payload to PDF (no bars there — colour is what that module will not do — so the ordering is the only thing carrying the emotions ranking on paper, and the intensity column comes before the day count to match what it is sorted on). Both are out of the views so they can be tested without a request, like `core/dashboard.py`.

- **Derived, never stored.** A report is rebuilt from `load_history` on every request — the same rows `/api/diary/` answers with, so a report and the archive can never disagree about a day, and the `MAX_HISTORY_ENTRIES` cap is inherited. Nothing is written to `raport`. That is fine while past entries are immutable (only today's is editable, and today is always in the week in progress, which has no report), but it means a report is not a document with a date on it — changing this file changes what last month's report says.
- **It used to run in the browser** (`frontend/src/utils/reports.ts`), and the move fixed two things beyond the PDF: the "has this week ended" cutoff is now read in `settings.TIME_ZONE`, the same clock that decided which calendar day an entry belongs to (from the client, a week the backend already considered over looked current for a few hours west of Warsaw), and there is one document rather than one per browser. `utils/reports.ts` is now formatting only; `api/reports.ts` is the mapping layer.
- **An emotion row carries both numbers**: `days` (how many days it was rated on) and `avg_intensity` (the mean of those ratings, on the chips' own 0-10 scale). The average is over *the days it was rated*, not over the seven days of the week — a chip the patient never touched is not a rating of nought, and counting it as one would pull every emotion down in proportion to how often they skipped it. Never null: a row exists only because the emotion was rated at least once. The ranking **orders by `avg_intensity`** and the bar length measures it too, against the 0-10 scale itself rather than against the longest row — the section is "Najsilniej odczuwane emocje". It used to rank and draw by `days`, on the argument that a single very bad day should not outrank a feeling that ran through the whole week; that argument is fair about *ordering* and was the wrong one to let decide the *bar*. Week 2026-08-24 is what settled it: 'Smutek' was rated on five days at an average of 0.8/10 and drew a bar 83% as long as the week's strongest feeling, while 'Spokój' at 6.3 drew the same bar as 'Lęk' at 2.5 — a specialist reading those lengths sees a sad week the diary does not describe. Ties break on `days`, then on declaration order. The scale being absolute is the second half of the fix: relative to the top row, the strongest feeling fills the bar whether it averaged 9 or 1.5, so a calm week and a desperate one draw the same picture. `days` stays on every row as the second number, the summary chips still compare it week to week, and the narrative summary now names the *strongest* emotion (`Najsilniej odczuwana emocja: …`) rather than the most frequent — naming a strongest-first row with a frequency would be a false claim in a document a therapist reads. **The ranking is not capped** — every emotion the week rated gets a row, up to the ten the vocabulary holds. An emotion nobody touched simply has no row: absence is what "not felt this week" looks like, and a cut list would read as emotions that were not felt rather than as ones that did not fit. `TOP_TRIGGERS` (4) still caps the other ranking, where the list is unbounded free text.
- **`frontend/src/types/report.ts` is the contract** and the payload is that shape, snake_cased. A `Delta` travels as a structure — signed value, unit, tone, and which of *two* reasons a number is missing (`no-previous-week` vs `unrated`, because saying "there is no previous week" about a week that exists and simply skipped a question would be false in a document a therapist reads). Each surface words it itself: `formatDeltaSentence` for a card, `report_pdf.format_delta` for print, which spells the gap out because a printout cannot be hovered over.
- **Tie-breaks depend on emotion declaration order** being identical in `core/emotions.py` and `frontend/src/utils/emotions.ts`. `test_emotions.py` now pins the order as well as the names.
- **`GET /api/reports/<week-id>/pdf/`** carries a `PdfRenderer` in its `renderer_classes` and overrides `finalize_response`. Neither is decoration: DRF negotiates content *before* the handler runs, so without a renderer declaring `application/pdf` a caller sending `Accept: application/pdf` — which is what `apiDownload` sends — is answered **406** and the view never runs; and once negotiation picks that renderer, a 404 would be served as `application/pdf` (a file the browser offers to save) unless error responses are forced back to JSON. Nothing is ever rendered through `PdfRenderer`; the view returns bytes ReportLab already produced. It answers `application/pdf` with `Content-Disposition: attachment` (an ASCII filename by construction, so no header encoding), `Cache-Control: no-store` (health data leaving as a file must not sit in a cache), and a throttle of its own (`ReportPdfThrottle`, `30/hour` per account) because laying out a document is CPU on a synchronous worker. The document carries **the patient's e-mail**, under the entry count: a printout that reaches a specialist has to say whose week it is. That address is the only thing in it from user_db, and the view reads it off the session at render time — `core/reports.py` aggregates medical_db and never sees one, so the two halves still only meet in application code. Nothing *else* identifying goes in (no `id_medical`, no user id, nothing in the PDF metadata). **The technique catalogue has two halves, merged by slug.** The techniques the app ships with are hardcoded in `frontend/src/data/techniques.ts`, transcribed from the client's DBT materials and **still awaiting clinical review**; the ones specialists write live in medical_db's `technique` table (widened by `0013` to hold the same structure) and arrive from `GET /api/techniques/`. `utils/techniques.ts` merges the two — built-in first, and a slug claimed by both keeps the built-in one, so the merge fails towards the reviewed text. Moving the hardcoded half into the database is the obvious next step and deliberately not part of this change: that text is under review, and a copy in a database nobody reviews is how the reviewed version stops being the one on screen.

- **Published means every patient**, not only the author's own — the decision behind the feature, which is why there is no per-patient assignment table. `author_id_specjalist` records who to ask about the wording and gates `PUT`/`DELETE` (`find_for_specjalist`); correcting a colleague's clinical text is a conversation, not a form. The column **never travels**: resolving a specialist's name would mean reading user_db from a medical_db row, and this project keeps that meeting point in exactly one named module (`core/account.py`).
- **The panel has no draft state and no per-technique safety flag.** Both checkboxes were on the form and were **removed on request**: everything a specialist saves is in every patient's catalogue immediately, and `pages/SpecialistTechniqueForm.tsx` says so in a line above the form instead of asking. `description_ready` and `availability` are therefore not inputs on `TechniqueSerializer` — `_fields` sets them to True/'ogolna' — so a hand-made body cannot hold a technique back either. Withdrawing one means deleting it.
- **The two columns stay, and so do the gates in `published()`**, which is worth being clear about because it now looks like dead code and is not. `published()` requires `description_ready` *and* `availability == 'ogolna'` *and* a slug: the first is what keeps the rows `mock_data.sql` seeds out of the catalogue (they hold a name and a sentence, not a technique), the second is the flag the source material asks for on the four techniques with medical contraindications — which live in the hardcoded half — and a safety flag that withheld nothing would be worse than none. They also still travel on the wire, because `isPublished` in `utils/techniques.ts` reads them for the built-in half and one payload shape is better than two. If the client ever asks for drafts or for unlocking a technique per patient, the form is where they come back, not the schema.
- **`GET /api/techniques/` refuses nobody who is signed in, but the app routes only patients and specialists there.** The endpoint is not behind `_require_patient` — a catalogue of published descriptions is not a record about anybody — and `test_techniques.py` pins that a guardian may read it. The *route* is a different matter: `RequireAuth` sends a guardian to `/parent`, and `HeaderMenu`'s `GUARDIAN_ITEMS` offers them no catalogue entry. That is the pre-existing guard rather than a decision about guardians, and it is worth a word with the client: parents are a target group in the client's own materials ("jak uprawomocniać innych — matters, parents are a target group"), so letting them read the same skills their child reads may well be wanted. Opening it is one `allowGuardian` on that route plus a menu entry — do not do it without asking, and do not read the API's permissiveness as the answer.
- **The vocabularies are shared strings, not translations.** `core/technique_vocabulary.py` holds the same literals as the union types in `types/technique.ts`, because they travel on the wire and end up as keys into the label maps in `utils/techniques.ts`. `test_techniques.py` parses the `.ts` file and compares both directions, and does the same for `BUILTIN_SLUGS` against the ids in `data/techniques.ts` — the same guard `test_emotions.py` puts on the emotion names. - **`schools` and `steps` are JSONB.** A technique can genuinely belong to two tabs at once, and a `technique_step` table would buy nothing: a step has no identity, nothing queries one, and the list is written and read as a unit by the form that edits it.
- **The slug is immutable once set**, and a change is refused rather than ignored: it is in the URL of a technique patients may already have opened, and freeing the old slug for something else is worse than refusing to rename. `PUT` replaces rather than merges, the same rule as `/api/diary/today/`.
- **The form does not ask for the slug; `utils/slug.ts` derives it from the name.** It used to be its own input, under a hint explaining that it had to be "małe litery bez polskich znaków, cyfry i łączniki" — i.e. asking a psychotherapist to perform a transliteration and to know what a slug is. `techniqueSlug` does it instead, and its whole job is that **every branch returns a value the backend accepts**: `TechniqueSerializer.slug` is a `RegexField(r'^[a-z0-9]+(-[a-z0-9]+)*$', max_length=64)`, so a malformed one would be a 400 on a field that is no longer on screen — a save that fails with nothing visible, the same failure the registration form had with `invitation_code`. Three details are load-bearing. `ł` is mapped **before** NFKD, because it has no canonical decomposition and would otherwise be dropped rather than folded ("łatwy" → "atwy") — the same trap `normalize_emotion` documents on the backend. The **`id-` prefix** means a technique written in the panel can no longer take a slug the hardcoded, clinically-reviewed half owns, which makes `SLUG_BUILTIN` unreachable from this form; it is `id-` rather than the `id_` originally asked for because the regex rejects an underscore. And **an edit sends the stored slug back verbatim** (`toInput`, no input touches it) rather than re-deriving it — the backend *refuses* a rename, so re-deriving would make renaming a technique, an ordinary edit, answer 400 under an invisible field.
- **A slug refusal is therefore shown under "Nazwa techniki"**, the input that actually produced it, worded as the name being taken — the argument being that with the shape and the built-in collision both ruled out, `SLUG_TAKEN` is the only reachable one. Worth knowing that the derivation is **lossy**, so that message can also appear for two names that are not the same: "Uważność: 5 zmysłów" and "Uważność 5 zmysłów" produce one slug, as do two names sharing their first 61 slug characters. Rare, and the specialist is told to change the name, which does fix it — but the message names a duplicate they will not find in the catalogue.
- **The patient's screens fail soft on this half.** `hooks/useStoredTechniques.ts` returns an empty list and a `failed` flag rather than an error page: the built-in catalogue needs no network, so a failed request must not take it down — the screen says in one line that some entries may be missing, because the one thing a catalogue must not do is silently omit something.

**Nawodnienie: `/diet/hydration` (`pages/DietHydration.tsx`) and `/api/diet/hydration/`.** §08 of the mockups is "Nawodnienie i suplementy"; this is the first half of it, and the first thing in the diet module with a database behind it. `core/drinks.py` is the vocabulary and the numbers, `core/hydration.py` the aggregation (out of the views like `core/dashboard.py`), `core/models.Hydration` the table, `frontend/src/utils/drinks.ts` the frontend half of the vocabulary.

- **Four rules come from the client and are not free choices**, each one a thing a later pass would "improve":
  1. **One daily goal, expressed in glasses**, with three ways to add — "+ Szklanka" (250 ml), "+ Butelka" (500 ml) and a custom amount. It is a *display target*, not clinical advice: this app is not entitled to tell anybody how much to drink, and a psychodietitian setting it per patient is the obvious next step (a column on `patient`, not an edit to `DAILY_TARGET_GLASSES`).
  2. **The goal is a point of reference, never a verdict.** "Po przekroczeniu celu pasek po prostu jest pełny. Nie ma gratulacji, serii ani komunikatu o niedoborze." So `progress` is capped at 1 for the bar while `glasses` is not (the day still says what it was), and there is no streak, no flag and no wording anywhere that a day could fail. `test_hydration_api.GoalTests.test_nothing_in_the_payload_is_a_verdict` sweeps the payload for one and `DietHydration.test.tsx` sweeps the screen.
  3. **Other drinks are recorded and never converted into water.** Herbata, Kawa, Napar ziołowy, **Woda z cytryną** and Kompot are a vocabulary with no coefficient anywhere near it — "decyzja merytoryczna zostaje po stronie specjalisty". Water with lemon sitting among them is the client's call, not a rounding nobody got to. A tap on a chip records a serving and moves no water figure, and the screen **says so in a line above the chips**, because a counter that does not move after a tap otherwise reads as a bug. `test_drinks.py` greps both modules for a per-drink number.
     **A patient can now type a drink of their own and give any drink a size**, and the two changes together cost the rule its structural guarantee — which is the thing to understand before touching this module. `drink` is free text rather than a `ChoiceField`, and an amount is accepted on every drink rather than on water alone. Each was worth having (five chips is the commonest drinks, not all of them; how much tea somebody drank is information they may want kept), but between them they removed the two things that made "nie przeliczamy na wodę" impossible to break: a closed name list, and non-water servings having no number to add. **What holds the rule now is that exactly two places compute the figure and both filter on `drink == WATER`** — `build_hydration_day` and `_week`. Nothing else in the module touches the total, and nothing else may: `test_hydration_api.WaterIsTheOnlyOneCountedTests` is the sweep, deliberately written with litre-sized amounts so a bug that added them would be unmissable rather than a rounding. See the typed-drink and amount notes below.
  4. **"Ostatnie 7 dni"**, water only, today last and marked. Drawn against the goal rather than against the tallest column — the same argument the weekly report's emotion bars settled: relative to the best day, a week of one glass draws the same picture as a week of eight.
- **The numbers are computed once, on the server.** `glasses` is `water_ml / GLASS_ML` to one decimal (400 ml is 1,6 glasses; rounding it to 2 would report back more than was entered), and the scale, both servings, the goal and the custom-amount bounds all travel on the wire so **nothing in the frontend hardcodes 6 or 250**. `utils/drinks.ts` formats and declines; it does not recompute.
- **A row per serving, not a counter column.** A counter makes "+1" a read-modify-write two taps in the same second can lose, and it leaves nothing to undo. Rows also make the chart a GROUP BY. `POST` therefore answers with the **whole rebuilt day** rather than the row it wrote — three figures move when one glass is recorded, and rebuilding them in the browser is how one day ends up with two versions of itself.
- **Every drink may carry an amount, and a serving that gives none is a glass.** The "Inne napoje" card has one optional `Ile? (ml, opcjonalnie)` input, read at the moment a chip is tapped and applied to a typed drink too. One input for the whole card rather than one per chip: the question is the same for all six, and six inputs would turn a row of chips into a form. **It empties itself after every serving**, which is not tidiness — an amount left behind would silently attach itself to the next tap, and 300 ml recorded against a tea nobody measured is the sort of thing somebody finds in their own records a week later and cannot explain. Both refusals this endpoint used to raise are **gone**: `AMOUNT_NOT_FOR_DRINK` with the rule that made the conversion structural, and `AMOUNT_REQUIRED`/`DRINK_IS_WATER` with the default below — typing "woda" into the name box now records exactly what "+ Szklanka" records, so there is nothing left to refuse. The serializer has no `validate()` at all any more.
- **`DEFAULT_SERVING_ML` is a number nobody typed, and that is the thing to weigh before touching it.** One tap means "I drank a glass of it", so `add_entry` stores `GLASS_ML` when no amount is given — for water and for everything else. It enters a clinical record and, on water, moves the goal bar, which is exactly the sort of default this project is otherwise careful not to invent: `emptyDraft` in `pages/DiaryEntry.tsx` wrote a 0 nobody chose and that was a defect. **What makes this one defensible is that the patient is told** — the hint under the amount box says "Bez podanej ilości zapisujemy szklankę (250 ml)", `DietHydration.test.tsx` pins that sentence, and the default has to go if it ever does. It is a separate constant from `GLASS_ML` rather than an alias in use, because "what the + Szklanka button pours" and "what an unmeasured serving is assumed to be" are two facts that happen to share a value. **Nothing was backfilled**: NULL is what every serving written before it holds, and the list still renders those as a drink with no size.
- **`entryLabel` checks the drink before the amount**, and that ordering is a fix rather than style: it used to reach "Szklanka · 250 ml" for anything carrying a number, which was safe only while nothing but water could carry one. With amounts on every drink — and now on *every* serving, since one with no size given is a glass — a tea was about to be listed as a glass of water on the one screen whose whole rule is that it is not. A non-water serving reads "Herbata · 250 ml".
- **The bounds apply to any amount, not to water's**, and the hint below the input states them rather than only enforcing them (a control that refuses with no reason beside it is the failure the registration form had). An out-of-range number disables the chips instead of being sent, so the refusal is on the screen rather than in a 400.
- **A typed drink is folded onto a chip whenever it matches one**, case- and whitespace-insensitively (`drinks.normalize_drink`): "herbata", "HERBATA" and "  Herbata " are all the chip's own `Herbata`. Without it one patient's list shows the same drink two or three ways depending on how they happened to type it, which is what makes a record read as unreliable. The folding lives **on the server alone** — `utils/drinks.ts` deliberately holds no copy, because two definitions of "is this the same drink" is the drift the shared vocabularies are tested against. `MAX_DRINK_NAME` (40) travels on the wire like the amount bounds, so the input caps itself at what the serializer takes.
- **The one name the form refuses is water's own**, and *where* it is refused is the point. Water is recorded with an amount and the typed-drink form asks for none, so accepting "woda" would write a serving of water of no size. The refusal therefore lands under **`drink`** — the box the patient typed into — pointing at the buttons that do take an amount. Answering it under `amount_ml`, a field that form does not render, would be a save failing invisibly: the failure `Register.tsx` had with `invitation_code`. The rule lives in `validate()` rather than `validate_drink` for exactly this reason: whether water is allowed depends on the amount, so a body that names water *and* an amount (the "+ Szklanka" shape, or a hand-made request) is still fine, and a call with no `drink` key at all is answered on `amount_ml` where the missing thing genuinely is the amount. `test_hydration_api` pins both directions.
- **The typed-drink form closes on the answer, never on the tap.** Closing it optimistically unmounted the input and its error the moment somebody typed "woda", so the one refusal it can produce had nowhere to be shown — the save failed silently, which is the whole failure mode this screen's messages exist to prevent. `drink()` therefore returns whether the serving was written, and on a refusal the typed name stays on screen ready to be corrected.
- **"+ Inny napój" is not on the artboard**, like the undo on the entries below it, and for a similar reason: §08 draws five chips, and five chips is a list of the commonest drinks rather than of everything a person drinks. Worth confirming with the client, since it adds a control to their screen — as is the question it leaves open, whether a typed drink should be able to carry an amount. Today it cannot, exactly like the five chips, and that consistency is what makes the water total provably water.
- **Today is editable and nothing older is**, which is the psychotherapy diary's rule applied to a second kind of row rather than a new one. `DELETE /api/diet/hydration/<id>/` filters on `id_medical` *and* on today, so somebody else's serving and yesterday's both answer 404 — the same convention as `/api/diary/<id>/`, and nothing leaks about whether the row exists. **The undo is not on the artboard**: §08 draws three add buttons and no way back, which on a phone is a stray tap you cannot correct. Worth confirming with the client, since it adds a control to their screen.
- **`MAX_ENTRIES_PER_DAY` (40) is a backstop, not a product rule**, counted inside the write's transaction so two taps cannot both see 39. It bounds the *data* rather than the request rate, which is why this endpoint carries **no throttle**: a rate cap here would be reachable by somebody genuinely tapping "+ Szklanka" a few times in a row, and what is worth protecting is the table.
- **Both gates apply, and the guardian one is the point.** It is a clinical endpoint like any other — `_require_patient` refuses a guardian and a specialist rather than answering them zero glasses, and an unlinked minor is refused, because a glass of water logged against a named account is health data. It is in `test_guardian_gate.clinical_urls` and in `test_consent_gate.all_urls` (which `test_password_gate` reuses), so all three sweeps cover it.
- **§08's other half is now its own screen** — see the supplements section below. The hydration screen still says nothing about it, for the reason it always did: naming a second feature on one screen answers in markup what belongs in the menu.
- **`--color-water*` are new tokens in `styles/theme.css`**, not three literals: on that screen the water colour is the thing being measured (the figure, the bar, seven columns), while every button stays sage like every other action in the app. The home card's bar moved onto the same tokens, so the two screens agree.

**Suplementy i leki: `/diet/supplements` (`pages/DietSupplements.tsx`) and `/api/diet/supplements/`.** The second half of §08, and its own screen because the mockups make it one. `core/supplements.py` holds the rules, `core/models.Supplement` + `core/models.SupplementIntake` the two tables, `frontend/src/utils/supplements.ts` the wording.

- **What §08 says this is**: "lista z dawką, częstotliwością, godziną oraz datami rozpoczęcia i zakończenia", with "Odhacz, kiedy weźmiesz" above it. Every one of those is a column and none of them is computed from anything.
- **A tick is a row for a day, and unticking deletes it.** Which is the load-bearing consequence: **nothing in this app stores that somebody did *not* take a medicine.** An absent row is a question nobody answered, there is no third state on a checkbox, and there is therefore no column an adherence score could be built from. Recording a missed dose would be a judgement the app is not entitled to make. A row per (supplement, day) rather than a boolean on the preparation, the same argument `hydration` makes for a row per serving: a column would be a running value two taps can race, it could not be undone per day, and it could not answer "did I take it on Tuesday" at all. The unique constraint `(id_supplement, entry_date)` is what makes a double-tapped checkbox one row, so ticking twice succeeds — like accepting a guardian invitation twice.
- **Nothing on the screen is a score, and that is the rule it is most worth defending.** §08 states it about the water counter — "nie ma gratulacji, serii ani komunikatu o niedoborze" — and it matters more here: among these patients are people with eating disorders and this is a list opened every morning. So there is no "2 z 3", no bar, no percentage and no wording that names a dose as missed, skipped or overdue. `DietSupplements.test.tsx`'s "what this screen refuses to show" sweeps for each, and `test_supplements_api.NothingIsAVerdictTests` sweeps the payload. The one place a count appears at all is the list's `aria-label`, where it says what the ticks already say visually; `takenCount` in `utils/supplements.ts` carries that restriction in its docstring and has exactly that one caller.
- **Only `name` is required.** Somebody who knows they take magnesium and not the dose has to be able to write it down — §05's "żadne pole nie blokuje zapisu" applied to this form. A blank answer is normalised to NULL on both sides, so "not answered" has one representation rather than two. `end_date` NULL means **bezterminowo**, the artboard's own wording, rather than an unanswered question; there is no third column for its "od 3 marca, wg zaleceń lekarza" variant, because `frequency` is free text and that is where it goes. The one refusal the form can produce is an end date before the start, raised under `end_date` so it lands on the input that gave it.
- **Only today is tickable**, which is the diary's rule applied to a third kind of row: whether a medicine was taken on Tuesday is a fact about Tuesday, and answering it on Friday would make the record no better than the memory. The day comes from the server's clock, so a date in the body reaches nothing (`test_supplements_api` pins it). A past day's tick is left alone and not shown.
- **Two things differ from the artboard, both deliberately.** *The reminder switch is not a global toggle*: a reminder is per preparation (each has its own hour), so the question is asked in the form that writes one and stored on `reminder_enabled` — and the card that replaces the switch says the thing that actually matters, that **this deployment sends no notifications at all**, no push and no mail, so the setting is kept and nothing fires on it yet. A switch that silently promised one would be the mistake the home screen's technique card was; the column exists so that the day a scheduler arrives it reads a value rather than asking everybody again. *And there is an "Edytuj" and a "Usuń"*, which the artboard has neither of — a mistyped dose on a medicine list has to be correctable. Deleting **asks twice** and says the ticks go with it (`supplement_intake` is CASCADE), the same two-step `SpecialistPatients` uses for ending care, because a stray tap on a phone would otherwise take an entry and its history.
- **PUT replaces rather than merges**, the same rule as `/api/diary/today/` and the technique form: the form submits its whole state, so a cleared dose is an answer taken back rather than one left unchanged. Every write — create, edit and the tick — answers with the **whole rebuilt list** rather than the row it touched, because the list is ordered by hour and a new row rarely belongs at the end; rebuilding that order in the browser is how one list ends up with two versions of itself.
- **Somebody else's row answers 404, never 403** (`supplements.find` filters on `id_medical` alongside the id), the same convention as `/api/diary/<id>/` — a 403 would confirm the row exists. `MAX_SUPPLEMENTS` (60) is a backstop counted inside the write's transaction, not a product rule; like the hydration endpoint this one carries **no throttle**, because what is worth protecting is the table and a rate cap would be reachable by somebody entering a real regimen of five preparations in one sitting.
- **A failed load says the server's own sentence**, and a generic "nie udało się wczytać" only when there was none. That is not a nicety: **every refusal a patient can actually reach here is a gate rather than a fault** — an account waiting on a guardian's acceptance (art. 8), or one whose consents are not in force — and each arrives with a message saying what to do about it. Both new diet screens threw that message away at first and were corrected; `pages/DietHydration.tsx` had the same flaw and was corrected with them, so the three screens now word a refusal the way `Journals.tsx` always did. Each pins it.
- **Both gates apply**, like every clinical endpoint: `_require_patient` refuses a guardian and a specialist rather than handing them an empty list, and an unlinked minor is refused. The new URLs are in `test_guardian_gate.clinical_urls` and `test_consent_gate.all_urls` (which `test_password_gate` reuses), so all three sweeps cover them.
- **`--color-supplement*` are new tokens in `styles/theme.css`.** The hour badge is the artboard's blue on its pale blue pill, with the *text* value darkened until it passes 4.5:1 on that background — the artboard's own #6e8fc7 reads at about 3:1, under the AA floor for the 12px it is used at. Every button on the screen stays sage, like every other action in the app.
- **The open question §08 states itself is still open**: whether this list is the same data as the health profile's "przyjmowane leki" (§13) or a second entry. §13 is not built and nothing else in this app holds a medicine, so this table is the only place one lives; when the profile arrives the decision is which of the two reads the other, never a third copy. The screen says nothing about a health profile, so silence cannot imply an answer (`DietSupplements.test.tsx` pins that too).

**Aktywność i sen: `/diet/activity-sleep` (`pages/DietActivitySleep.tsx`).** §09 of the mockups, both of its artboards, and **the one screen in this module with no backend of any kind**. `components/DietActivityPanel.tsx` and `components/DietSleepPanel.tsx` are the two halves, `utils/activity.ts` and `utils/sleep.ts` their vocabularies and their one calculation, `utils/dayLock.ts` the rule they share with the diary, `hooks/useCurrentDay.ts` the live clock that makes that rule bite.

- **Nothing it collects is stored anywhere**, and three separate pieces of wording exist because of it. `loadActivityDay`/`loadSleepNight` in `api/diet.ts` return the empty producers, both panels hold their entries in component state, and a reload loses them — while everything else on the screen reads as though that were untrue: two "Zapisz" buttons and a list headed "Zapisane dzisiaj". So `NOT_STORED_NOTE` sits above the switch; the sleep panel's confirmation says "Zapisano — na razie tylko na tej karcie" rather than "Zapisano.", because `role="status"` is announced on its own and the bare word would be the one thing on the screen actively claiming a save that did not happen; and **`dayLockNotice` now takes a `stored` flag**, which both panels pass as false. That last one was a self-contradiction in two consecutive paragraphs: the helper is borrowed from the psychotherapy module, where the entry really is kept, so it promised "Później zostanie zapisany na stałe" one line under the note admitting the opposite. The *deadline* half of that sentence is a rule and still holds; only the promise is dropped. This is the defect `0009` already was once. **Remove all three in the commit that wires the endpoints, not before, and do not soften any of them** — `utils/dayLock.test.ts`, the disclosure test in `DietActivitySleep.test.tsx` and `App.test.tsx`'s reachability block are what fail if they go early.
- **`sampleActivityDay`/`sampleSleepNight` exist and are wired to nothing**, which is the compromise that keeps the mockup's own figures off a patient's screen while leaving the filled state testable. Swapping them into the two `load…` functions is how to look at it; that they are dated relative to the day they are asked for is what stops them quietly becoming stale demo data.
- **Two artboards, one route, one menu entry.** §03 gives the menu a single "Aktywność i sen" and §09's note says the two are reached from it "w prototypie" by switching through the menu — a limitation of a click-through prototype, not a design decision, since in a real app it would mean leaving the screen to reach its other half. Hence the segmented `tablist` and the roving tabindex. **Both panels stay mounted with the inactive one `hidden`**, and that is correctness rather than taste: rendered as a ternary, switching to "Sen" destroyed a patient's typed activities and step count, and nothing persists them.
- **The day lock is the trap worth reading `utils/dayLock.ts` for.** The screen fixes `today` at mount and the loaders derive the day's `date` from it, so comparing the two asked `x === x` and enforced nothing — a form opened at 23:55 went on offering to write into Tuesday at 00:10 on Wednesday. The second argument therefore comes from `useCurrentDay()`. And a lock is not a substitute for a correct stamp: `newActivityEntry` reads the clock at save time, because a refused save is a control that misbehaved while a row filed under the wrong day is bad data in a document a specialist reads.
- **A night carries the date of the morning it ended on** — filled in on Friday, it is the night from Thursday to Friday. Nothing in the data says so (23:40 and 06:50 read equally well as either day, and the two answers put the night in different weeks), so the rule is stated at the field in `types/diet.ts` and argued in `utils/sleep.ts`. The night's length is the **only** value this module computes anywhere, derived from the two hours rather than stored beside them.
- **Nothing here is measured, scored or compared**, the rule §08 states and this screen inherits: no calories burnt, no intensity, no pace, no heart rate, no step goal, no sleep score, no weekly average, no seven-night chart (the mockup's other variant draws one), and nothing relating sleep to meals or to mood — that last is a specialist's reading and belongs to the analysis screen, not to the form that collects it. Steps are a property of the **day** rather than of an activity, null until somebody types one, and null is not zero. `DietActivitySleep.test.tsx` sweeps for each absence.
- **An untouched control is not an answer**, which is why the duration stepper stores null while rendering `ACTIVITY_DURATION_DEFAULT` — `emptyDraft` in `pages/DiaryEntry.tsx` learned that the hard way. The edge it leaves (recording exactly 30 minutes takes moving the control off 30 and back) is pinned rather than hidden, and "Nie podaję czasu" is the way back to unanswered that every other control on the form already had.
- **Both artboards are marked "Etap 2 — jeśli starczy czasu"**, so this is deliberately the smallest genuinely usable version and nothing on it is a placeholder for a richer one. What it needs before it does anything is the pair of endpoints: `diet_activity` (a row per entry, plus the day's step count — which has nowhere to live on an entry) and `diet_sleep` (a row per night, keyed on the morning). Both belong next to `core/meals.py` and `core/hydration.py`, behind `_require_patient` like every other clinical endpoint, and both are in the three sweeps the moment they exist.

**Both list screens are paginated at 7 rows** (`hooks/usePagination.ts`, `components/Pagination.tsx`). Client-side, and that is a constraint rather than a shortcut: `/api/diary/` and `/api/reports/` answer with everything, and "Dzienniczki" filters what it already holds — paginating on the server while filtering in the browser would hand out pages of the wrong list. So this is a readability feature, not a payload one; the day `MAX_HISTORY_ENTRIES` becomes a real ceiling instead of a backstop, filtering and paging have to move to the backend together.

- The page lives in `?page=`, not in component state, so opening a row from page three and pressing back returns to page three. It is clamped rather than trusted (`?page=99` shows the last page, `?page=abc` the first), and page one is left out of the URL so `?page=1` and the bare address are not two addresses for one screen.
- **Journals paginates the filtered list and resets to page one when the filter changes** — page four of "Wszystkie" is rarely page four of "Dobre dni", and landing on an empty page reads as "no such days" rather than "wrong page".
- `goTo` scrolls to the top (`RouteChange` only watches the pathname, and this is a query change); `reset` deliberately does not, because a filter chip is pressed from the top already.
- The control renders nothing at one page, and shows prev / "Strona X z Y (a–b z N …)" / next rather than numbered buttons: a year of reports is fifty-odd pages, which is a row of buttons nobody can use on a phone.

**The app shell.** `App.tsx` wraps every route in four things a single-page app has to do by hand, because a real page load does them for free:

- `components/RouteChange.tsx` sets `document.title` from `ROUTE_TITLES` (keyed by route pattern, matched with `matchPath` so `/reports/:id` resolves), scrolls back to the top, and announces the new screen through an `aria-live` region. Titles live in `routes.ts` rather than in each page because the announcement has to happen when the URL changes and a page's own effect runs after that — it would name the screen the user just left. The first render is skipped: the browser has already scrolled and read the document.
- `components/OfflineBanner.tsx` (+ `hooks/useOnline.ts`) says the device is offline. Advisory only — `navigator.onLine` says the device has *a* connection, not that our API answers, so it never gates a request. It exists because every screen words a failure as "Nie udało się wczytać…", which invites an immediate retry and is the wrong advice for a phone in a lift.
- a skip link onto `<main id="main">`. `#main` carries `display: flex; flex-grow: 1` in `index.css` so the `#root > main > .*-page` flex chain still lets a screen fill the viewport.
- `*` renders `pages/NotFound.tsx` instead of redirecting to `/modules`, which made a mistyped address look like it had worked.

`src/index.css` is the global baseline and nothing more. It used to carry the Vite starter's own design system next to the project's — a purple accent, code/social styling, and **`color-scheme: light dark` with a dark palette**, which on a device in dark mode asked the browser to render native controls (date pickers, selects, slider tracks) dark on top of the app's white cards. The app is deliberately light-only. What is left is the font baseline, a zero-specificity `:focus-visible` floor (`:where(...)`, so every screen's own focus style still wins), a `prefers-reduced-motion` block, and `.visually-hidden`/`.skip-link`. `src/App.css` was 180 lines of starter markup styling that nothing imported; it is gone.

**The document's font family is `--font-body` itself, and that is a fix rather than tidiness.** `:root` used to set `font: 18px/145% system-ui, …`, so Karla arrived only where a rule said `font-family: var(--font-body)` — which is why almost every rule in every stylesheet repeats that declaration ~60 times, and why the rules that *forgot* it rendered in the user agent's face right next to the ones that did not. `index.css` also gives `button, input, select, textarea` a `font-family: inherit`, because form controls do not inherit it (a UA default, not a cascade rule) — that one line is what makes an input which says nothing about type still render in Karla. A missing declaration is now invisible instead of a visible mismatch, so the repeated ones in the older stylesheets are redundant rather than load-bearing; the three areas rewritten in this pass dropped theirs.

**`src/styles/theme.css` is the token layer, and `src/styles/panel.css` is the panel screens' shared frame.** theme.css used to hold only colours, fonts and one shadow, so everything else drifted: the same 1px card edge existed in five weights (tint at .1/.12/.18/.2/.25) and the same content card in six radii (12/14/16/18/20/24), each picked per file. It now names them by role — `--color-divider`/`--color-border`/`--color-border-strong`, `--radius-control`/`-tile`/`-card`/`-surface`/`-pill`, `--shadow-card`/`-soft`/`-raised`, `--focus-ring`, `--color-surface`/`--color-surface-quiet`, `--color-caution` (the readable ochre that was hardcoded as `#8a6416` in three files) and `--panel-width`. **Add a value there before adding it to a screen.** panel.css is the frame, greeting block, sections, cards, figure tiles and controls shared by `/parent` and `/specialist` — the two screens that are somebody's whole view of the app without being a patient's. Before it, both were dressed in `moduleSelect.css` (the *patient's* module chooser) plus `parentHome.css`, so the specialist panel was laid out by classes called `.parent-page` and `.parent-menu` and pulled in four stylesheets to draw a heading; the chooser keeps `moduleSelect.css` to itself now. **The panel screens' action colour is sage, not graphite.** `.specialist-form-submit`, the caseload's invite button and `.specialist-invitation-accept` were graphite while every other primary action in the app (`.auth-submit`, `.today-add-button`) was sage, which read as a different product on the one screen a specialist crosses into `/profile` from. They are `.panel-button` now. `.caseload-section`/`.child-card` and friends keep their names as identity hooks (and test selectors) but carry no shape rules of their own, and the status wording on those screens is `.panel-note`/`.panel-error`/`.panel-success`/`.panel-empty`/`.panel-loading` rather than a per-component class. One wart to know about: `.panel-empty`/`.panel-loading`/`.panel-quiet` carry `max-width: var(--panel-width)`, and on the specialist sub-screens they render as direct children of `.journals-page`, whose `> *` rule sets 640px at **identical specificity** — which of the two wins is decided by the bundler's emit order (today it resolves to 640px). That is the same fragility this pass removed from `.specialist-list`; scoping the width to `.panel-page` is the fix if it ever moves.

**`box-sizing: border-box` is global, and it closed two horizontal scrollbars rather than tidying anything up.** The declaration used to sit in 34 individual rules, which made every new rule pairing a width with a padding a fresh candidate for the same bug: `.technique-row` rendered 316px wide inside a 280px column and `.consents-card` 336px, hanging 8px off each side of the page. Three more rules with the identical pattern — `.journal-row`, `.report-row`, `.diary-entry-collapse-toggle` — were saved only by being `<button>` elements, which the user agent stylesheet already gives `border-box`. The reset is `*, *::before, *::after` in `index.css`. **It changes what an existing `min-width` means**, so four rules sized under the old model were compensated by hand, each carrying its arithmetic in a comment: `.home-menu-dropdown` 260→284, `.auth-info-tile` 140→168, `.technique-badge` 46→64, `.report-hero-button` 180→216. The last of those is on a `<button>` — i.e. an element that already had `border-box` — so unlike the other three it is genuinely 36px wider than before, on "Pobierz PDF" on both report screens; the comment there and the one in `index.css` currently contradict each other, and that is the one to settle when these numbers are next touched.

**Touch targets follow WCAG 2.5.8 (24×24 AA) and aim for the 44px both mobile platforms recommend, using two techniques that are not interchangeable.** A control gets real height (`min-height: 44px` on the filter chips, the emotion chips, the pagination buttons, the panel buttons, the analysis picker) because it is a box already. A **link** that sits in a line of text gets an `::after` pseudo-element stretched to 44px instead (`.auth-link-button`, `.auth-info-button`, `.mood-chart-link`, `.journals-back`, `.profile-inline-button`, `.panel-link`), because giving those real height would push the layout around them — `.mood-chart-title-row` aligns on the baseline, the consent card's stack would grow, and `.panel-link` shares a row with `.panel-button-quiet` on every patient card. The checkbox inputs went 18→24 (the RODO consents in registration, and the confirmations that mirror them), and the smallest type in the app went 11→12px — except two rules in `analysis.css` that keep 11px with the reason written down: the heatmap header column is `table-layout: fixed` at 68px, and `.analysis-bar-label` breaks "Frustracja" mid-word inside a 44px column at anything larger. `.analysis-bar` also gained `position: relative`, which is a bug fix rather than a touch target: without it the column's `.visually-hidden` label had the viewport as its containing block, escaped the scroll container and stretched the document 227px past a 320px screen.

**One thing in the app genuinely cannot be expressed in CSS, and `hooks/useMediaQuery.ts` exists for it alone.** `components/TrendChart.tsx` draws into a fixed `viewBox` scaled to fill its container, so a label's *rendered* size is its declared size times `containerWidth / VIEW_WIDTH` — a factor running from about 0.72 on a 320px phone to 1.78 once the content column stops growing. At the single 9px the chart used to carry, the axis numbers rendered at a comfortable 16px on a monitor and a measured 6.5px on a phone, and the correction is a division by that scale factor, which `calc()` cannot express. So `AXIS_NARROW`/`AXIS_MEDIUM`/`AXIS_WIDE` pick a size per breakpoint (narrowest match wins; no match is the unchanged desktop branch) and hand it to the stylesheet as `--analysis-axis-size`. Each of them carries a `spacing` that **has to move with the size**: it is how close two `dd.mm` ticks may sit in viewBox units, so raising the type without raising it trades an unreadable label for two overlapping ones. The hook is a media query and not a measurement — no `ResizeObserver`, no `getBoundingClientRect` — and a missing `window.matchMedia` reports "does not match", which lands every caller on the widest branch.

**A session that ends while the app is open** is handled by `api/client.ts` dispatching `UNAUTHORIZED_EVENT` on any 401/403 and `auth/AuthProvider.tsx` deciding what it means. The split is the point: the client knows about fetch and cookies and should not learn about React state, and 403 is *also* the normal answer to `/api/auth/me/` for a visitor and the answer to a stale CSRF token. So the provider ignores the event when nobody is signed in, and otherwise **re-asks `/api/auth/me/`** rather than assuming — only a confirmed `null` clears the session. A failed check leaves the user signed in, because a network blip must not throw away a form somebody is filling. Concurrent refusals collapse into one check.

**Leaving "Dodaj wpis" with unsaved changes** asks first. `dirty` compares the draft with the last server-agreed state by value, so a change made and undone is not a change. It covers `beforeunload` (reload, closed tab, back out of the app) and the screen's own back arrow; **a header-menu link still navigates away silently** — `<Routes>` cannot block in-app navigation without a data router. Saving marks the draft clean before navigating, or the guard would ask about the changes just written, and passes `state: { savedEntry: true }` so `/home` renders the confirmation — shown there rather than on the form, which navigates away before a message could be read.

**`apiRequest` prepends nothing, so every path it is given has to start with `/api/`** — `BASE_URL` is the *origin* (empty for same-origin), and the prefix is the caller's job. That is a convention rather than a mechanism, and it is exactly what one module got wrong quietly: `api/diet.ts` was written with `'/diet/hydration/'`, which reached the **Vite dev server as a page address**, came back as a 404 carrying HTML, and — because `firstMessage` can pull no message out of HTML — surfaced as the generic "Coś poszło nie tak". On `/diet` not even that, since the hydration card swallows its own failure by design. Nothing failed loudly, and **no unit test noticed, because a test that mocks `apiRequest` asserts the path its own caller passed** — the assertion pinned the bug. `client.test.ts` now reads every module in `src/api/` (via `import.meta.glob(..., '?raw')`, since there is no `@types/node`) and fails on a literal path without the prefix, naming the file and the path; it also counts what it parsed, so a regex that stopped matching fails instead of going quiet.

**Frontend/backend wiring.** `frontend/src/api/client.ts` is the only place that knows about `credentials: 'include'` and the `X-CSRFToken` header (including one silent retry with a fresh token on a 403, for when the server restarted). Its `firstMessage` walks **objects as well as arrays**, which matters more than it looks: DRF answers a `many=True` field with one object per item (`{"steps": [{"description": ["…"]}]}`), and without that branch every nested error came back as no message at all — the screen showed "Coś poszło nie tak" over a body that said exactly what was wrong. A screen that can name the position should still check the value itself before submitting, because the index does not survive the trip (see `emptyStep` in `pages/SpecialistTechniqueForm.tsx`). `frontend/src/api/auth.ts` is the single translation point between the form's camelCase field names and the API's snake_case columns, in both directions — including `REGISTER_FIELDS`, which is what lets a Django field error land under the right input. `src/auth/` holds the session context that `App.tsx`'s route guards wait on.

In development the frontend talks to `/api` on its own origin and `vite.config.ts` proxies that to `http://127.0.0.1:8000` (override the target with `API_PROXY_TARGET` in `frontend/.env.local` if Django listens elsewhere). That keeps the session cookie first-party and avoids CORS entirely, but **not** Django's CSRF origin check: the proxy rewrites `Host` to the target, so `http://localhost:5173` has to be in `CSRF_TRUSTED_ORIGINS` or every POST comes back 403 with "Origin checking failed". Pointing `VITE_API_BASE_URL` at a backend on another origin instead makes every call cross-site, which needs `DJANGO_CROSS_SITE_COOKIES=true` on the backend plus the frontend's origin in both `CORS_ALLOWED_ORIGINS` and `CSRF_TRUSTED_ORIGINS`.

`migrate core --database=default` / `migrate core --database=medical` create the actual domain tables — see the reconciliation caveat above before running either against a real database.

**`scripts/setup_dev.sh` is the one command that cannot forget the second database**: it migrates `default` *and* `medical` (with `--fake-initial`, since `database_setup.sql` creates the schema) and then runs `check_databases`. Idempotent and data-safe, so it is also the right thing to run after a `git pull` that brought migrations. It deliberately does **not** create or seed the databases — that needs the container and the SQL scripts and is destructive; `markdown/serwery.md` has that sequence.

**`manage.py seed_demo_diary` exists because one screen cannot be reached by using the app.** The guardian panel's attention marker fires on the child's *most recent weekly report*, and a report only exists for a week that has **ended** — so seeing it by hand means having written entries last week, which no amount of clicking today produces. The command writes them: `EMAIL=FLAGGED_DAYS` per patient (the marker needs `RISKY_DAYS_FOR_ATTENTION`, so `=3` marks and `=2` does not, which is the pair worth seeding), `--entries` for how many days of the week get an entry at all. Three properties are deliberate. It **refuses to run with `DEBUG=False`**, because what it writes is fabricated clinical content against a named account and a mis-set `DJANGO_ENV_FILE` must not be one keystroke from putting invented self-harm notes in somebody's record. It is **idempotent per week** (it deletes the rows it finds in that week first), or a second run would put two entries on one day — which the app itself forbids. And it looks a patient up **by e-mail and follows `patient.id_medical` across**, which is why it is a command rather than SQL: `mock_data.sql` seeds accounts by literal UUID, while this writes into accounts somebody registered through the app, over a join Postgres does not enforce. It prints whether the marker came out set, by asking `account.last_report_needs_attention` rather than by restating the rule. **It also seeds the diet module now**, and that half is on a different clock: the diary entries go into last *completed* week because that is the only week a report exists for, while every diet screen shows today and the last seven days — so the meals, the water and the supplement list run from six days ago to **today**, or all four screens would be empty after seeding them. `--no-diet` turns that half off. It is shaped rather than uniform: one day of the seven holds no meal (so the streak breaks somewhere and the history has a gap, which every real diary has), one meal carries no kind and one no hour (so §05's "no field blocks a save" branches are reachable from a seed), some days are under the water goal and some over it (the goal is a point of reference, and a seed that always met it would make the screen look like it rewards that), and two of §08's three preparations are ticked off for today — exactly the state its artboard draws. Water is written as *servings* rather than a total, so the rows add up the way a real day does; `test_seed_demo_diary.py` is what checks that they do, along with the streak, the gap and the idempotence.

**`manage.py check_databases` fills the one edge of the schema triangle nothing else covers.** `test_schema_sync.py` compares `database_setup.sql` with `core/models.py`, and `makemigrations --check` compares `models.py` with the migration state — but **nothing compared a real database with the models**, which is precisely where a faked `0001` plus two migration histories goes wrong: a `migrate` that hit `default` only leaves medical_db behind, the imports and the whole test suite still pass, and the first request to `/api/dashboard/home/` answers 500 with `column diary.tension_level does not exist`. The command checks reachability, unapplied migrations per database, every model column against `information_schema` (routed per model, so a medical table is not looked for in user_db), and the `throttle_cache` table — that last one because its absence makes the rate limits **fail open** silently. Read-only and exit-code driven, so it works as a CI step and, more to the point, as the post-deploy smoke test for Azure: `DJANGO_ENV_FILE=.env.azure python manage.py check_databases`. A column the database has and the models do not is a *warning*, not a failure (an un-run `0006` looks exactly like that), or the command would be unusable mid-migration. It is the only module in `core`/`config` allowed to hold a database cursor — `test_security_guards.SqlInjectionSinkTests.CURSOR_ONLY` lists it with its reason and pins that it still runs no statement of its own.

### Docker
```bash
docker build -t mediculus-backend .
```
The `Dockerfile` only packages `backend/` (installs `requirements.txt`, copies `backend/` in, runs `gunicorn config.wsgi:application` on port 8000 as a non-root `django` user). The frontend is not part of this image.

## Infrastructure

Backend dev deployment runs on Azure App Service (`mediculus-dev`), backed by Azure Postgres (two databases as above), with credentials/registry info supplied via `.env`-style App Settings (`DJANGO_REGISTRY_NAME`, `DJANGO_LOGIN_SERVER`, `DJANGO_USERNAME`, `DJANGO_PASSWORD` are ACR credentials, not app credentials). Treat DB and ACR passwords as live secrets — they are not meant to be pasted into chat/commits.
