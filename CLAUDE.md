# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

Mediculus is a mental-health / wellbeing tracking platform (emotion diary, DBT technique tracking, mood scales) aimed at patients (including minors, via a parent/guardian account), specialists (psychotherapists, dietitians), and their supervising organization. The project is early-stage: the domain model is designed (see `ERD/DIAGRAM.drawio*`), registration/login work end to end (DRF endpoints under `/api/auth/`, wired to the React pages), and the patient home screen now reads the signed-in patient's real diary data (`/api/dashboard/home/`). What is still missing is everything that *writes* clinical data — there is no way to create a diary entry or rate a mood scale through the app; those rows only arrive via `scripts/mock_data.sql`. Weekly reports are generated (`/api/reports/`, including a PDF export) but **derived, not stored**: nothing has ever written a `raport` row, which is also why the dashboard's technique suggestion only ever shows seed data.

Repo layout:
- `backend/` — Django project (`config/` settings/urls) plus one app, `core/`, holding all domain models across both databases (see Architecture).
- `frontend/` — Vite + React PWA scaffold (`vite-plugin-pwa`).
- `scripts/` — hand-written SQL that defines and seeds the actual database schema (see below — this is not Django migrations).
- `ERD/` — entity-relationship diagram for the two databases.
- `markdown/` — internal planning/requirements notes (Polish); not code documentation.

## Architecture

**Two independently-managed Postgres databases**, both configured in `backend/config/settings.py` `DATABASES`:
- `default` → `user_db` — identity/PII data: `user`, `user_role`, `specjalist`, `patient`, `parent_child`.
- `medical` → `medical_db` — pseudonymized clinical data: `diary`, `mood_scale`, `technique`, `raport`.

The split is intentional (data pseudonymization): `medical_db` rows reference patients only via `patient.id_medical`, a UUID that is **not** a real foreign key across databases — it's a logical/application-level join only (see comments in `scripts/database_setup.sql`). Never assume Postgres will enforce referential integrity between the two DBs; that has to be handled in application code.

**Domain schema lives in Django models + migrations (app `core`).** `backend/core/models.py` mirrors `scripts/database_setup.sql` (same table/column names via `db_table`/`db_column`). All models live in a single app spanning both databases, and `core/routers.py` (`CoreDatabaseRouter`, wired via `DATABASE_ROUTERS`) maps them by name: everything in `MEDICAL_MODELS` goes to `medical`, the rest to `default`. The router implements `db_for_read`/`db_for_write`, so `Diary.objects.all()` reaches `medical_db` on its own — `.using('medical')` is no longer required (it still works, and is harmless to keep).

Data migrations in `core` need care: `allow_migrate` receives `model_name=None` for `RunPython`/`RunSQL`, so pass `hints={'target_db': 'default'}` (or `'medical'`) on those operations to pin them to one database. Without a hint they run against **both**, which fails loudly rather than being silently skipped — see `core/migrations/0002_align_faked_schema.py` for the pattern.

Two DBs mean two independent migration histories: run `python manage.py migrate core --database=default` for the `user_db` models and `python manage.py migrate core --database=medical` for the `medical_db` models — a plain `migrate core` only targets `default`.

`0001_initial` is applied as **faked** everywhere, because `scripts/database_setup.sql` had already created the tables. Consequences worth knowing:

- Setting up a new environment means running `database_setup.sql` + `mock_data.sql` first, then `migrate --fake-initial` on both databases (`markdown/serwery.md` has the exact sequence). Letting migrations create the schema from scratch instead would work, but then `mock_data.sql` fails — its INSERTs omit `created_at`/`updated_at`, which only have database defaults in the SQL script, not in the Django-generated schema.
- Faking means Django cannot see drift between the two "sources of truth". `0002_align_faked_schema` exists precisely because `database_setup.sql` had shipped `TIMESTAMP`/unbounded `VARCHAR` where the faked state recorded `timestamptz`/`varchar(255)`. If you change one of the two, check the other by hand — `makemigrations` will not warn you.

Both Azure databases were at `0001` (faked) when that was last checked, on 2026-08-28 — the date is part of the claim, because nothing in the repo tracks the deployment's migration state and `0009` was added later without re-checking it; `DJANGO_ENV_FILE=.env.azure python manage.py check_databases` is what answers it for real. `0002`–`0009` have only been applied locally and need `migrate` on Azure — **on both databases**, which is the trap: a plain `migrate core` targets `default` only, and a `medical` left behind at `0004` fails with `column diary.tension_level does not exist` on the first request to `/api/dashboard/home/`. Four of them are written as `SeparateDatabaseAndState` with `ADD COLUMN IF NOT EXISTS`, because `database_setup.sql` declares the same columns and the documented setup order runs that script first: `0004_user_consents` adds the two RODO consent timestamps to `"user"`, and `0005_diary_entry_fields` adds the columns the "Dodaj wpis" form needs — `tension_level`, `emotion_note`, `thought`, `risky_behavior_note` on `diary`, plus `shame_scale`/`calm_scale` on `mood_scale`. `0005` targets medical_db only, so its `RunSQL` carries `hints={'target_db': 'medical'}`. `0006_drop_overall_feeling` then removes `diary.overall_feeling`: the "jakość samopoczucia" slider that would have filled it was cut from the entry form and `current_mood` already records how the patient says they feel, so it was a duplicate with no source. It is the first destructive migration — the text `mock_data.sql` used to seed there is not recoverable by reversing it. `0007_parent_child_accepted_at` adds `parent_child.accepted_at` (user_db, so `hints={'target_db': 'default'}`): NULL is a guardian invitation nobody has answered, set is the moment it was accepted — see the guardian-invitation notes below for why a refusal deletes the row instead of filling a third column. `0009_diary_time_of_day` adds `diary.time_of_day` (medical_db, so `hints={'target_db': 'medical'}`), the entry form's "pora dnia" question — one of `morning`, `noon`, `evening`, `night`, or NULL. It closes a **silent data loss**, not a missing feature: the form had been sending the key for a while and `DiaryEntrySerializer` is a plain `serializers.Serializer`, which discards a key it does not declare *without an error*, so the patient picked "Wieczór", was told the entry had been saved, reopened it and found the question blank. Which is why the serializer now names the field as a `ChoiceField` rather than accepting free text: an answer outside the four buckets is a 400, and the one thing it must never be again is quietly dropped. Deliberately **not** backfilled — nothing in an older row says what time of day it describes, so NULL there is the correct value rather than a gap to fill. The vocabulary lives in `core/time_of_day.py` and holds **only** the four keys: 'Rano'/'Południe'/'Wieczór'/'Noc' belong to `frontend/src/utils/timeOfDay.ts`, and a second copy in Python would be one that can quietly disagree — the opposite arrangement to `emotions.py`, where the Polish name *is* the stored value. Nothing pins the two lists together yet, because the frontend half is still unmerged (it lives on `frontend-analiza`, `b7c116d`, so on `main` nothing sends the field): when that branch lands, `timeOfDay.ts` wants the same cross-language check `test_emotions.py` runs over the emotion names. The ERD (`ERD/DIAGRAM.drawio`) was brought back in step with `0006` and now lists `diary` and `mood_scale` in the same order as `database_setup.sql`, `time_of_day` included — `0009` added that row to the `.drawio` by hand. What is still behind: **the diagram does not show `parent_child.accepted_at`**, and the `.png`/`.pdf` exports are behind on both it and `diary.time_of_day` — all three are edited/generated by hand (there is no drawio CLI on the dev machine), so bring them in step after any schema change, this one included. `test_erd_sync.py` is what notices when they drift: it parses the `.drawio` XML and compares it column-for-column with the models, with `KNOWN_ERD_GAPS` as an explicit to-do list of what the picture is missing (an empty dict being the goal). Nothing checks the exports at all.

Also be aware there will be two parallel notions of "user" in `user_db`: Django's own `auth_user` (created by `manage.py migrate` for the built-in apps, used only for `/admin/` login) and `core.User` (the hand-mirrored `"user"` table, the actual domain/app user). They are intentionally not connected — don't conflate them.

A few `on_delete` choices in `core/models.py` are a deliberate improvement over the raw SQL, which specifies no `ON DELETE` action (i.e. Postgres `NO ACTION` everywhere): `User.user_role` and `Raport.technique`/`Patient.specjalist` use `PROTECT`/`SET_NULL` instead, chosen per-relationship for sane application behavior rather than mirrored verbatim.

**Env-var-driven settings, no defaults for required values.** `settings.py` reads `DJANGO_SECRET_KEY`, `DJANGO_DEBUG`, and all `USER_DB_*` / `MEDICAL_DB_*` DB credentials via `os.environ[...]` (not `.get`), so the process will hard-fail at import time if any are missing — always ensure `.env` is populated (see `.env.example` for the full list) before running anything backend-related. `CORS_ALLOWED_ORIGINS`, `CSRF_TRUSTED_ORIGINS` and `DJANGO_ALLOWED_HOSTS` are optional comma-separated lists (whitespace around entries is stripped; origins must include a scheme). Two optional flags default to their Azure-safe value, so the deployment needs no App Setting for either: `DB_SSLMODE` (default `require`; set `disable` for the local container) and `DJANGO_USE_PROXY_SSL_HEADER` (default `true`; set `false` for a directly-reachable server, since otherwise a client can spoof `X-Forwarded-Proto` and make `request.is_secure()` lie).

**Authentication: DRF endpoints under `/api/auth/`, session cookie, custom user table.** `core/urls.py` (mounted at `api/` by `config/urls.py`) exposes `csrf/`, `register/`, `login/`, `logout/`, `me/`, `guardian/`, plus `/api/guardian/invitations/` and `/api/account/` (see the profile section below). The pieces worth knowing before touching them:

- **`core.User` is not an auth user.** `django.contrib.auth.login()` would write an `auth_user` primary key into the session, so it is unusable here. `core/authentication.py` borrows only the session framework: `start_session()` stores the domain user's id under `core_user_id`, and `SessionUserAuthentication` (the project-wide `DEFAULT_AUTHENTICATION_CLASSES`) reads it back. `core.User` carries an `is_authenticated = True` class attribute purely so DRF's `IsAuthenticated` can duck-type it.
- **`IsAuthenticated` is the default permission** and `UNAUTHENTICATED_USER` is `None`, so a new endpoint that declares no `permission_classes` is closed rather than accidentally public. `CsrfView`/`RegisterView`/`LoginView` opt out explicitly.
- **CSRF applies to `register/` and `login/` too**, via a hand-applied `@csrf_protect` — DRF marks every `APIView` csrf_exempt, and the usual enforcement lives in the authentication class, which does nothing for a caller who has no session yet. `GET /api/auth/csrf/` both sets the cookie and returns the token in its body; the body copy is what a frontend on another site uses, since it cannot read the API's cookies.
- **A rejected CSRF check answers in JSON** (`CSRF_FAILURE_VIEW` → `core/csrf.py`), because Django's own failure view renders HTML that a `fetch()` cannot read — the frontend was falling back to a generic "something went wrong" and discarding the only useful detail. The technical `reason` is included only when `DEBUG`; in production it goes to the log instead, which is also why `settings.LOGGING` exists: Django's default console handler carries a `require_debug_true` filter and the only other one mails admins about `ERROR`s, so a CSRF rejection (a `WARNING`) reached **nothing at all** with `DEBUG=False`.
- **Login answers identically for a wrong password and an unknown address**, and spends the same time on both (`_get_unmatchable_hash` in `core/serializers.py`) — for a mental-health service, who has an account is itself sensitive. `_password_matches` also survives the literal `'mock_hash_placeholder'` that `mock_data.sql` seeds, which would otherwise make `check_password` raise.
- **The registration form's "account type" choice drives the schema**, via `ACCOUNT_TYPES` in `core/serializers.py`: `patient` → role `patient` + `Patient(is_child=False)`, `minor_patient` → role `patient` + `Patient(is_child=True)`, `parent` → role `rodzic` and **no `Patient` row at all** (a guardian is not a clinical subject, so they get no `id_medical` and nothing in `medical_db` can refer to them). `is_child` comes from that choice, not computed from `date_of_birth`, but `_check_age_matches_account_type` refuses the two combinations where they would contradict each other (an adult date on a `minor_patient`, a minor's date on a `patient`) — otherwise a later feature trusting one column over the other would silently be wrong about some records. The boundary lives in `ADULT_AGE`, a policy constant rather than a fact: RODO art. 8 uses 16 for consent to digital services, so it may need revisiting. A `parent` is deliberately not age-checked. Roles are looked up by name and come from `mock_data.sql`, not a migration, so a database missing the row yields `role: null` rather than a failure.
- **A minor's account is blocked until a guardian accepts it.** Two halves, and the split is the point — naming somebody is a request, accepting is the consent a minor cannot give for themselves (RODO art. 8):
  - `POST /api/auth/guardian/` (the child) names the guardian by e-mail and creates a `parent_child` row with `accepted_at` NULL. **The address has to belong to an account whose role is `rodzic`** — `GUARDIAN_ROLE` in `core/serializers.py` reads that name out of `ACCOUNT_TYPES` so the registration form and this one cannot disagree. A patient's address, a specialist's, an account with no role and an address nobody registered all get the **same** rejection: telling them apart would turn the form into a way to ask who has an account here and of what kind. The child's own address is the one exception, answered specifically (mirroring `parent_child_not_self`) because it is a mistake they can act on. One pending invitation at a time, so a child cannot fish for whichever adult answers first; re-sending it to the same guardian is idempotent. **`validate()`'s order is load-bearing:** `ALREADY_LINKED`/`ALREADY_INVITED` describe the child's own account and are raised *before* the role is looked at, because the other way round a child holding any link got `ALREADY_INVITED` for a `rodzic` address and `NOT_A_GUARDIAN` for everything else — a working probe for whether an address is a guardian account, which is precisely what the shared message exists to prevent. It also equalizes the query count across addresses, so the answer does not leak by timing either.
  - `DELETE /api/auth/guardian/` (the child) withdraws a *pending* invitation, so a mistyped address that happens to belong to a real guardian is not a dead end. It refuses once accepted: undoing a link is not the child's decision, or the guardian's oversight would last exactly as long as the child allowed it.
  - `GET /api/guardian/invitations/` + `POST .../<uuid>/accept/` + `POST .../<uuid>/reject/` (the guardian). Filtered by `parent=request.user`, so somebody else's invitation answers exactly like a nonexistent one (404 — a 403 would confirm it is real), the same convention as `/api/diary/<id>/`. Accepting twice succeeds (a double-clicked button); **refusing deletes the row** rather than marking it refused, which puts the child back to naming somebody else instead of leaving them with a "no" nobody can act on. An already-accepted link is not refusable here — withdrawing one is a different decision, with a live account behind it, and belongs to the parent panel.
  - The rules live in `core/guardian.py`, out of the views so they can be tested without a request. `accepted_at` is a timestamp rather than a boolean for the same reason as the consent columns on `user`: RODO art. 7(1) puts the burden of proof on us and "yes" without a date proves nothing.
- **`UserSerializer.guardian_status` is what gates the frontend**: `'none'`, `'pending'` or `'accepted'`, and `null` for everyone the question does not apply to (an adult patient, a guardian, a specialist). Only `'accepted'` unblocks the app. `App.tsx`'s `RequireAuth` sends any other minor to `ROUTES.linkGuardian` and `RequireGuardianLink` pushes everyone else off that screen; `needsGuardianLink` in `src/api/auth.ts` deliberately **fails closed** on `null`, since letting an unvouched-for child write health data is the worse way to be wrong. `LinkGuardian.tsx` has two states off the same status — the form, then the wait (check-again / withdraw, and nothing that could accept on the guardian's behalf).
- **The gate is enforced on the API too, in `_require_patient` (`core/views.py`).** It used to live only in `App.tsx`'s route guard, so a hand-made request from an unlinked minor's session reached the diary, the dashboard and the reports — and RODO art. 8 makes a minor's consent the guardian's to give, not something a route guard can be the only record of. `require_guardian_link` **defaults to True** for the same reason `IsAuthenticated` is the default permission: a clinical endpoint added later that never thinks about the gate is closed rather than accidentally open. Exactly one caller opts out — `GuardianLinkView`, i.e. `POST/DELETE /api/auth/guardian/`, which is how the child asks for the acceptance in the first place; gating it would be a deadlock, and that is why the gate is a parameter on the shared helper rather than a permission class over every view. `/api/auth/me/` and `logout/` stay open as well: the route guard reads `me` to learn *why* it was refused. The refusal is 403 with its own message (`GUARDIAN_GATE_REFUSAL`) rather than the "tylko dla konta pacjenta" one, which would be false here — the account *is* a patient's, it is waiting on somebody else. The condition mirrors `needsGuardianLink` in `src/api/auth.ts` character for character (`is_child` **is True** *and* status not `'accepted'`; a truthiness test would gate an `is_child` NULL row, and keying on `guardian_status` being `null` would have locked out every adult patient). Nothing enforces that the two definitions stay in step — change them together. `test_guardian_gate.py` sweeps every clinical URL from one place, because a gate applied to `/api/diary/` and forgotten on `/api/reports/` is not a gate — `/api/account/profile/` is in that sweep. `POST /api/account/password/` deliberately is **not** gated and is pinned as such: everyone has a password, including the accounts that are not clinical subjects, and a minor waiting on a guardian who has reason to change theirs must not be told to come back once somebody else answers a form.
- **The guardian answers on `/parent`**, above the placeholder, via `components/GuardianInvitations.tsx` — the first and only screen a guardian lands on after login, because a child is blocked until it is answered and a card behind a menu would be one nobody finds. It used to sit on `/modules`, which was where every account landed; it moved with the guardians when they got a view of their own (see the parent view below), and moving it was not optional — leaving it on a screen they can no longer reach would have stranded every child mid-signup. No other account renders it, so none fires the request. A failed load says so rather than drawing nothing: silence would read as "nobody asked" while a child waits on the other side of it. The card carries the child's name and address and nothing clinical — accepting is a decision about a person, not a look at their diary.
- **Still missing:** a guardian cannot *undo* an accepted link, and nothing notifies them out of band — an invitation is only visible to a guardian who logs in.

**The parent view: `/parent` (`pages/ParentHome.tsx`), one screen and a placeholder.** A guardian is not a clinical subject — no `patient` row, so everything behind `_require_patient` answers them 403 — and they were nevertheless being dropped on the patient's module chooser and offered a tile into `/home`, which then failed on a refusal the screen could only word as "coś poszło nie tak". What is on the screen is the invitations card (real, and the reason the screen is not *only* a placeholder) and one large placeholder for the rest of the panel.

- **The placeholder deliberately does not say what a guardian will see of the child.** That is undecided and is not a UI question: the diary is health data the child writes about themselves, the reports are written for the treating specialist, and this app's one firm rule in the area runs the other way (a patient cannot cut the specialist off — see `pages/Reports.tsx`). Naming "podgląd dzienniczka dziecka" on a placeholder would answer it in markup, and a client reviewing the screen would reasonably read it as settled. `ParentHome.test.tsx` pins the absence.
- **The redirects live in three guards in `App.tsx` and one helper.** `homeRouteFor(user)` is where "which landing screen does this account have" is decided, used by `GuestOnly`, `/` and `RequireGuardianLink`. `RequireGuardian` guards `/parent` itself. And `RequireAuth` gained **`allowGuardian`, defaulting to false** — the same shape as `require_guardian_link` on `_require_patient` and for the same reason: a patient screen added later that never thinks about the question sends a guardian to their own screen rather than to a refusal. **Exactly one route opts out: `/profile`**, and that is a real exception — identity, the consent register (art. 7(3)) and the password form all work for a guardian, and the one thing on that screen that does not is `GET /api/account/profile/`, which the screen itself only asks for when `hasPatientProfile`.
- **`HeaderMenu` is role-aware** (`GUARDIAN_ITEMS`): the parent screen and the profile, nothing else. It has to agree with the guards above — a menu entry the router immediately undoes is worse than no entry — so change the two together.
- **`GET /api/guardian/children/` is what the panel reads** (`GuardianChildrenView` → `guardian.accepted_children` + `account.build_linked_children`; rendered by `components/GuardianChildren.tsx`). Filtered by `parent=request.user` with no permission class of its own, the same convention as the invitations list, and **accepted links only** — reporting on a child before their guardian answered would be the gate working in one direction.
- **It answers with engagement and never with content**, and that is a decided line rather than a first pass: entry count, streak, and the date of the last entry. No mood, no emotions, no stress or energy, no risky-behaviour flag, no report figures, no entry text, no `id_medical`. `CHILD_SUMMARY_FIELDS` in `core/account.py` is the list and carries the argument; `test_guardian_children_api.NothingClinicalTests` sweeps the whole payload for leaks, because the failure mode is somebody adding `avg_mood` here and it looking like an improvement. The reason is clinical rather than squeamish — a minor who knows a parent reads their diary writes a different diary, which is the same argument the client made when she refused to let a patient cut the specialist off. **Whether a guardian may ever read the content is still undecided and is not a UI question**; the card says out loud that they are not reading it, so silence cannot imply otherwise.
- The figures come from `diary.count_entries`, `dashboard.streak_days` and `diary.last_entry_date` — the same functions the child's own screens use, so a parent and a child cannot be told different things about one diary.
- **Nothing else on the backend changed for the panel.** `/api/guardian/invitations/` already served guardians and every other endpoint already refused them.
- **`UserSerializer` carries the consent register**, `data_consent_at` and `services_consent_at` — the columns `0004` added and registration writes. They ride on `/api/auth/me/` rather than on a profile endpoint because they are columns on the same `user` row the rest of that payload comes from, and two endpoints answering for one row is two endpoints free to disagree. Sent as the stored moment rather than a date or a boolean (art. 7(1) again), NULL meaning never granted — which is what lets the profile render "Nieudzielona" as a fact instead of inferring it, and is the state every row `mock_data.sql` seeds is in. `0010` added the other half, `data_consent_withdrawn_at` / `services_consent_withdrawn_at`, and the payload carries the pair plus a computed `active` per consent under **one** `consents` key — the flat `data_consent_at` / `services_consent_at` fields are gone from the wire on purpose; see the consent gate below. `UserSerializer` also gained **`is_patient`**, which is simply whether a `patient` row exists — `_require_patient`'s first check, sent rather than inferred. The obvious inference is wrong: `is_child` is None *both* for an account with no patient row and for a patient row that never answered the question (nullable column, and `mock_data.sql` predates it being set), so `isChild !== null` in the frontend would have hidden the profile's counters from a patient the backend happily serves. The serializer also **caches the `patient` lookup per user**: `is_child` and `guardian_status` both need it and the second calls the first, so this was three queries on the endpoint the frontend hits at every app start and after every 403.
- **Password strength is checked with the user, not without one.** `check_password_strength(password, user)` in `core/serializers.py` is the single entry point, and it exists because `validate_password(value)` — no second argument — silently disables `UserAttributeSimilarityValidator`: it returns immediately when `user` is None, so a password identical to the account's own e-mail passed registration. Nothing about the call looked wrong, which is why it survived; the only symptom is from outside. Registration therefore runs it from `validate()` rather than from a `validate_password` method, where `attrs` already holds the address and the name, and hands it an **unsaved** `User` (the validator only reads attributes off it). `AUTH_PASSWORD_VALIDATORS` names `user_attributes` explicitly — Django's default list is `username`/`first_name`/`last_name`/`email`, three of which `core.User` does not have, so without it the check would only ever look at the address.
- **`LANGUAGE_CODE = 'pl'`**, so Django's own messages (password validators, DRF's "not authenticated") reach the Polish UI in Polish.
- **Rate limiting** is two independent caps on `login/`, and they answer different attacks. `LoginAccountThrottle` (scope `login_account`, `15/hour`) counts attempts against **one account**, keyed on an HMAC of the address the form submitted — read from the raw body, not from a user that was found, so an address nobody registered costs exactly what a real one does and the counter cannot become the enumeration oracle the login response deliberately is not. This is the cap that bounds password guessing: a botnet gives every attempt its own IP and its own per-IP budget, but they all land on the same account counter. A password that actually matches clears it (`reset()`), or somebody logging in from several devices in an hour would lock themselves out. It is **silent until `WARN_AT_ATTEMPTS_LEFT` (5) remain** — i.e. from the 10th failure — then folds "Pozostało N prób…" into `detail`, counting down to "To była ostatnia próba…" on the 15th; announcing the budget earlier would only tell an attacker how much room they have. Folded into `detail` as one string because `firstMessage` in `src/api/client.ts` renders a list's first entry and drops the rest. `ReportPdfThrottle` (`report_pdf`, `30/hour` per account) is a capacity cap rather than a security one — see the reports section. `PasswordChangeThrottle` (`password_change`, `10/hour` per account) is a security one again: `POST /api/account/password/` verifies the *current* password, so it is a second oracle for guessing it, reachable from a session left open on a borrowed phone — and the login cap counts nothing there, since a signed-in caller submits no address. Its own scope rather than the shared `'auth'` one, so that changing the login limit does not silently change this; `GuardianLinkThrottle` still shares `'auth'`, which is a wart worth fixing the same way. The per-IP cap on `login/`/`register/` is `10/min` (and `10/min` per account on `auth/guardian/`, via `GuardianLinkThrottle`, a `UserRateThrottle` — `AnonRateThrottle` exempts requests carrying a session, so the per-IP cap would have counted nothing there), counted in `CACHES['default']`, which is Django's `DatabaseCache` on a `throttle_cache` table in `user_db` (`core/routers.py` sends the non-`core` app label to `default` on its own). It used to be the default local-memory cache — per *process*, so every cap was worth as much as the number of gunicorn workers and the login limit bounded nothing in particular, since which worker answers is the load balancer's choice. There is no Redis in this deployment and a handful of counters does not justify adding one to run and pay for. Two details are load-bearing: the table is created by `0008_throttle_cache_table` rather than by a documented `createcachetable` step, because a missing table makes every cache write raise and DRF reads an unreachable cache as "no history" — i.e. the caps **fail open**; and `OPTIONS['MAX_ENTRIES']` is `20000` rather than Django's default `300`, because `DatabaseCache` culls once past it and a culled row is a counter back at zero, i.e. the cap failing open under exactly the load that caused the culling. `test_migrations.ThrottleCacheTableTests`/`ThrottleCacheSettingsTests` pin both, plus the fact that the migration's table name and the setting still agree. Both classes live in `core/throttling.py` and mix in `HashedIdent`, so the **cache key holds an HMAC-SHA256 of the caller's address rather than the address** — DRF writes that value straight into the key, and now that the cache *is* a table in `user_db` that is the difference between a counter and a log of client IPs sitting next to the PII — `HashedIdent` was written against exactly this move. Keyed on `SECRET_KEY` rather than a bare digest, since IPv4 is 2**32 values and an unkeyed hash of one pseudonymizes nothing. `NUM_PROXIES` is `1`: unset, DRF keys on the *whole* `X-Forwarded-For`, which the client writes, so a different value per request bought a fresh budget and the cap counted nothing. One trusted hop means the last entry is the address App Service actually saw; raise it if a proxy is added, and never set it to `0` behind one, which would put every client on the internet on a single counter.

**The profile's own endpoints: `/api/account/`.** Two, and the split between them is which database they need:

- **`GET /api/account/profile/`** answers with the two counters and the care card — everything on "Profil" that is neither identity nor consent. `core/account.py` is the aggregation, and it is **the one module in the project that reads both databases**: the counters come from medical_db through `id_medical`, the specialist from user_db through `patient.specjalist`. That meeting point is deliberately in one named place, so `core/dashboard.py`, `core/reports.py` and `core/frequency.py` can go on seeing nothing but a UUID. Behind `_require_patient`, so a guardian is refused rather than told they have written 0 entries and have no therapist — both true of a row that does not exist, and both reading as a clinical record. `hasPatientProfile` in `src/api/auth.ts` mirrors that rule so the frontend does not make the request at all; the refusal is there because a route guard is not enforcement.
  - **Neither counter is computed here.** `entry_count` is `diary.count_entries` and `streak_days` is `dashboard.streak_days` — the same functions behind `GET /api/diary/` and `GET /api/dashboard/home/`, which is why the latter is public rather than `_streak_days`. The profile is a summary of screens the patient can open, and a summary that disagrees with the screen it summarises is worse than none. `count_entries` is deliberately not capped at `MAX_HISTORY_ENTRIES`: that cap bounds a list, and a `COUNT(*)` has no such problem.
  - **`care` is nullable and so is its `approach`.** `patient.specjalist` is SET_NULL and an account registered before the first appointment has nobody assigned — an ordinary state the screen says in words. `approach` maps onto `specjalist.specjalization`, the closest thing the schema holds; treat a difference from the mockup's "nurt" as a schema question, not a mapping bug. **`phone` is always null**: no table holds a specialist's number, and `api/profile.ts` drops anything arriving under that key rather than trusting it — the safety plan renders a `tel:` link off it, and a live link that fails when tapped reads, in a bad moment, as the therapist's number being out of service. Where that number should live is a decision for the specialist panel.
- **`POST /api/account/password/`** changes the signed-in account's password and answers 204 with no body. The current password is re-asked and checked **server-side**: a live session proves the device, not the person holding it. It is validated for *presence only* — rows seeded by `mock_data.sql` and accounts created before the 8-character rule hold passwords today's validators would reject, and running them through would put "min. 8 znaków" under *Obecne hasło* and leave those accounts unable to submit the form at all. `src/components/ProfilePasswordForm.tsx` makes the same call for the same reason. The new password goes through `check_password_strength` with the user, so it can be refused for resembling the account's own address or name. **Other sessions survive**: ours carry `core_user_id` and no password hash, so nothing goes stale — signing an account's other devices out is a real feature, but it needs a way to enumerate its sessions, which this deployment has not got.
- **`POST /api/account/consents/withdraw/` and `.../restore/`** are the consent gate's two ends — see below.
- **Still stubs, each blocked on a decision rather than on effort** (`src/api/account.ts`, which rejects instead of faking success): account deletion needs the legal question about retaining clinical records answered first; the e-mail change is two endpoints, not one, because a new address has to be confirmed from a message sent *to it* and there is no mail out of this deployment; and data export (art. 15/20) is still owed after being removed from the screen.

**The consent gate: without both RODO consents, the app answers one screen.** `core/consents.py` holds the rule, `core/permissions.py` enforces it, `pages/ConsentsRequired.tsx` is the screen.

- **Withdrawing locks the account; it does not delete it.** The older reading — the app processes health data and nothing else, so losing the art. 9 consent ends the account — got the premise right and the conclusion wrong. Stopping the processing does not require destroying the record, and equating the two made exercising a right (art. 7(3)) irreversible an hour later when somebody changed their mind. Nothing is removed: the diary sits where it was and comes back unchanged when the consent does. **Deleting the account stays a separate, still-stubbed decision**, which is where irreversibility belongs. This also settles the `TODO(klientka)` on the services consent: the app *is* a service of the foundation, so both consents are required and neither is the milder one.
- **Withdrawal is its own column, not a cleared grant.** `0010` adds `data_consent_withdrawn_at` / `services_consent_withdrawn_at` to `"user"` (user_db, so the `RunSQL` carries `hints={'target_db': 'default'}`; `database_setup.sql` mirrors them). A consent is active when `granted_at is not None and (withdrawn_at is None or withdrawn_at <= granted_at)` — **written once, in `consents.is_active`**, because the permission class, the serializer and both endpoints all have to agree. Restoring writes a fresh `granted_at`, later than the withdrawal, which turns the comparison back on without erasing either event. That keeps the last cycle per consent, not a full audit log; a table is the answer if one is ever needed.
- **The gate is a default permission, not a shared helper.** The guardian gate lives inside `_require_patient` because every clinical endpoint already calls it; this one applies to *everything*, including endpoints that touch no patient row, so it goes in `DEFAULT_PERMISSION_CLASSES` next to `IsAuthenticated`. **The trap is that setting `permission_classes` on a view replaces the defaults wholesale**, so every exemption uses the named `CONSENT_EXEMPT` rather than spelling `[IsAuthenticated]` out — the exempt set is one grep, and `test_consent_gate.py` sweeps every registered URL to prove nothing else slipped out. Exactly four are exempt, each the gate's own escape hatch: `me/` (how the frontend learns *why* it was refused), `logout/`, and the two consent endpoints.
- **Both consents, not either**, and an account that never granted one is treated exactly like one that withdrew it — rows seeded by `mock_data.sql` have neither column set and belong on the same screen. `needsConsents` in `src/api/auth.ts` mirrors `has_active_consents` character for character; change them together. It **fails open** on a payload with no `consents` block, unlike `needsGuardianLink`, and deliberately: a deployed backend a release behind would otherwise black out every client, and the server refuses on its own regardless.
- **Restoring asks for no password.** It is the direction that *unblocks* an account, so friction costs somebody who changed their mind and protects nobody — whoever reaches the endpoint is already inside the session. Withdrawal keeps its password prompt.
- **The screen offers signing out at the same weight as restoring**, on purpose: a screen where restoring is the only escape is pressuring somebody into a consent, and a consent given under pressure is not one (art. 7(4)).
- **`AccountClosureConfirm` now shows two different lists** — "Co zostanie usunięte" for deletion, "Co się stanie" for a withdrawal that removes nothing. Reusing the first over a reversible act was a false statement on the one screen whose job is to be precise about consequences.
- **`active` travels on the wire and is never recomputed in the browser**, and that rule was bought with a bug. `consents` is a `SerializerMethodField`, whose return value the JSON encoder wrote as UTC with a `Z`, while the declared `data_consent_at` field went through DRF's `DateTimeField` and came out in `settings.TIME_ZONE` with `+02:00` — the same instant, twice, in two formats. `ConsentsRequired` compared them as **strings** to decide whether a consent still held, and `'…T10:…Z' <= '…T12:…+02:00'` is true, so a consent withdrawn a fraction of a second after it was granted read as active: the screen showed "Udzielona", rendered no restore button, and left the account with nothing but the logout link. Both halves are fixed — the method field renders through `serializers.DateTimeField` so one instant has one representation, and the duplicate top-level fields are gone so there is nothing to compare against — but the durable fix is that `core/consents.is_active` is the only place that comparison exists. `consentGrants` in `utils/consents.ts` keys on `active` for the same reason: `granted_at` survives a withdrawal (art. 7(1)), so keying on its presence listed a withdrawn consent as "Udzielona". `test_consent_gate.PayloadConsistencyTests` pins the rendering, and `ConsentsRequired.test.tsx` pins that a payload whose dates sort the wrong way as text still offers the consents back.
- **Withdrawal keeps the session.** The account still exists and its owner has to reach the screen offering the consents back; signing them out would put it behind a login they may not want to perform. Only deletion ends the session.

**The diary's own endpoints: `/api/diary/`.** `core/views.py` exposes three, and the split between them *is* the product rule — one entry per calendar day, editable on the day it was written, everything older read-only:

- `GET`/`PUT /api/diary/today/` — the only writable one, and it can only ever address today. `core/diary.py` `save_today_entry` replaces rather than merges: the form submits its whole state, so a field left out is an answer taken back, not one left unchanged.
- `GET /api/diary/` — the archive, newest first, today included. Read-only structurally rather than by permission: there is no write verb on the URL.
- `GET /api/diary/<uuid>/` — one past entry. The **only** diary URL carrying an id, and therefore the only one where a caller can name a row that is not theirs; `load_entry` filters on the session's `id_medical` alongside the id, so somebody else's entry answers exactly like a nonexistent one (404, nothing leaked about whether it exists). Route order matters: `diary/today/` is declared before `diary/<uuid>/`.

`serialize_entry` is shared by all three and carries `id` plus `saved_at` (`updated_at`, i.e. when it was last saved) on top of what the form edits — the archive needs both. `MAX_HISTORY_ENTRIES` is a runaway-query backstop, not a product limit; hitting it means the screen needs real pagination.

**The home screen's data: `GET /api/dashboard/home/`.** `core/views.py` `HomeDashboardView` answers with everything `frontend/src/pages/Home.tsx` draws — streak, today's entry, the 7-day chart, the stress/energy averages, the technique suggestion. The aggregation itself is in `core/dashboard.py`, kept out of the view so it can be tested (and reused by the analysis/report screens) without a request.

- **The session is the only identity input.** The view resolves `request.user` → `Patient.id_medical` (user_db) and passes that UUID to `build_home_dashboard`, which touches nothing but medical_db. There is no patient id in the URL, so one account cannot ask for another's numbers, and the aggregation code never sees a name or an e-mail.
- **An account with no `patient` row is refused, not answered with zeroes** — a guardian or a specialist is not a clinical subject, so an empty diary would be a misleading answer rather than a true one. Guardians get to a child's data through the parent panel, which does not exist yet (`parent_child` is still unwritten — see the note above).
- **`core/emotions.py` is the shared vocabulary**, and `frontend/src/utils/emotions.ts` holds the same ten names plus a colour for each. The strings have to match character for character: the API sends names and the chart looks up colours by them. Nothing enforces that — `api/dashboard.ts` treats a name it does not recognise as "no colour" rather than drawing an invisible bar.
- **One of the ten emotions has no scale column.** `mood_scale` covers nine (`shame_scale`/`calm_scale` were added by `0005`) and `diary.stress_level` supplies 'Stres'. A day can still legitimately have a named emotion and no intensity — rows written before `0005`, or an emotion named in `diary.current_strongest_emotion` that was never rated — which the chart draws as a fixed-height bar in that emotion's colour.
- **`current_strongest_emotion` wins over the sliders** when `normalize_emotion` can read it, with its height taken from the matching slider. Unmappable text — the seed data alone contains 'zmęczenie' — falls back to the highest rating instead of being forced into the nearest name. The column was designed to hold the patient's own answer to "what did you feel most strongly", but the entry form never asks that question, so `core/diary.py` derives it from the highest rating on save (`strongest_emotion`, sharing `dashboard._ratings`' tie-break order so the two can never disagree). Rows written before that, and the seed data, are the only ones where the column means anything else. If the form ever grows the question, that is the line that should start trusting the answer instead.
- **The technique suggestion is read from `raport`, not computed here.** Whatever produces the reports is where that judgement belongs; a second opinion invented on the dashboard would quietly disagree with the one in the reports screen. No report yet means no card.
- **`settings.TIME_ZONE` is `Europe/Warsaw`** (rows are still stored in UTC). It decides which calendar day a `created_at` belongs to, so under UTC an entry written at 00:30 would have counted towards the previous day.

**The "Raporty" screens are derived, not stored.** `frontend/src/pages/Reports.tsx` (the history) and `pages/ReportDetail.tsx` (one report) draw what `GET /api/reports/` answers — see the reports section below for how it is built. Derived on every request from the same rows `/api/diary/` returns, so no number on a report can disagree with the entries it came from; `raport` in medical_db is **still unwritten by anything**, which is a separate gap from the endpoint existing (see "Still to do" below).

The rules that shape those screens came from the client and are not free choices:

- **Reports are generated automatically, once a week**, from diaries and nothing else (confirmed twice). The patient does not create one and does not pick a range, so there is no generator UI and no Tydzień/Miesiąc/Kwartał switch — the mockup's pages 9-10 predate that decision. A quarterly report is an open question with the client; a daily one was rejected outright as a copy of the diary. `buildWeeklyReports` therefore skips the week in progress (a report exists once its week has ended) and any week with no entries at all (nothing to report on) — the latter also counts as "no previous week" for the week after it, so its deltas read as *brak poprzedniego tygodnia* rather than as a drop to zero.
- **Reports are visible to the specialists treating the patient, and only to them; the patient cannot cut that off.** Dropping a link is the specialist's action. The client's clinical reason: with eating disorders the tendency to hide information rises, so a patient-side switch would disable the feature exactly in the cases it exists for. This was contested earlier in the project, so `Reports.tsx` carries a TODO saying so — do not turn it back into an opt-in share step. Hence no "Wyślij terapeucie" button anywhere, only a plain informational note. "Pobierz PDF" stays, because saving a file to your own device is not an act of sharing; it is implemented (`GET /api/reports/<week-id>/pdf/`).
- **Changes are always a direction and a value** ("+0,6 od poprzedniego tygodnia", "Lęk −4 dni"), never an assessment of the patient, and an unfavourable move is ochre rather than the error red. Which direction is favourable is only asserted for the four metrics plus tension, because the app already asserts it elsewhere (the mood scale is ordered, "trudniejsze dni" says so in its name, and the sliders are labelled *wyczerpanie ↔ pełnia energii* / *rozluźnienie ↔ skrajne napięcie*). Emotion chips are deliberately untoned: whether more days of 'Lęk' is bad is a clinical judgement this screen is not entitled to make — see `tone()` in `utils/reports.ts`.
- **Risky behaviour reaches the reports** (the client asked for it; it is not in the mockup). Its section is rendered even when the week held none, because "none this week" is itself a reading for a specialist and a section that appeared only on bad weeks would announce them from the table of contents. Styling is the entry form's ochre, never red.
- **Two mockup sections are deliberately missing**, each with a TODO where it belongs: "Skuteczność technik" needs a way to rate a technique after applying it, and "Realizacja celów" needs the therapeutic-goals system. Both are extension-priority and neither exists, and a percentage computed from nothing would be a made-up number in a document a therapist reads.
- **A missing comparison is two different answers.** `Delta.gap` says which: `'no-previous-week'` is genuinely the first week, `'unrated'` is a week that exists and never answered that question (every field on the entry form is optional, so a patient can log seven days and skip the mood tiles throughout). They get different wording, in the cards and in the summary sentence, because "there is no previous week" is a false statement about a week that has entries in it — and it would be false inside a document a therapist reads.
- **The week-has-ended cutoff is read in `settings.TIME_ZONE`**, the same clock `core/days.py` uses to decide which calendar day an entry belongs to. It used to be read from the browser, which made a report appear a few hours late west of Warsaw; moving the aggregation to the backend is what fixed it.
- The narrative summary is composed from the same figures the cards show (`buildSummary`) rather than hard-coded, but it is still a placeholder: the real one belongs where the report is generated, next to the technique suggestion the dashboard already reads out of `raport`.

`src/utils/days.ts` and `placeLabel` in `src/utils/triggers.ts` were extracted while building this: `toIsoDate` had been copied into `Journals.tsx` and `DiaryEntry.tsx`, and the chip/"Inne" unpacking into `Journals.tsx` and `JournalDetail.tsx`. Both now have one definition, which is what lets a report count places the same way the diary displays them.

**Weekly reports: `/api/reports/`.** Two rules worth knowing before touching the numbers: `_round1` uses `Decimal`/`ROUND_HALF_UP`, not `round()`, whose banker's rounding sends 0.25 to 0.2 while sending 3.35 to 3.4 depending on where the float lands — unpredictable at the boundary is a poor property for a figure read clinically. And `_polish_key` compares `(base letter, diacritic rank)` pairs rather than appending a marker to the base letter: with 'ł' rendered as 'l' plus a low marker, the marker also sorts below every real letter and "Łódź" comes out before "Lublin". `core/reports.py` turns diary entries into one report per completed Monday–Sunday week; `core/report_pdf.py` renders the same payload to PDF (no bars there — colour is what that module will not do — so the ordering is the only thing carrying the emotions ranking on paper, and the intensity column comes before the day count to match what it is sorted on). Both are out of the views so they can be tested without a request, like `core/dashboard.py`.

- **Derived, never stored.** A report is rebuilt from `load_history` on every request — the same rows `/api/diary/` answers with, so a report and the archive can never disagree about a day, and the `MAX_HISTORY_ENTRIES` cap is inherited. Nothing is written to `raport`. That is fine while past entries are immutable (only today's is editable, and today is always in the week in progress, which has no report), but it means a report is not a document with a date on it — changing this file changes what last month's report says.
- **It used to run in the browser** (`frontend/src/utils/reports.ts`), and the move fixed two things beyond the PDF: the "has this week ended" cutoff is now read in `settings.TIME_ZONE`, the same clock that decided which calendar day an entry belongs to (from the client, a week the backend already considered over looked current for a few hours west of Warsaw), and there is one document rather than one per browser. `utils/reports.ts` is now formatting only; `api/reports.ts` is the mapping layer.
- **An emotion row carries both numbers**: `days` (how many days it was rated on) and `avg_intensity` (the mean of those ratings, on the chips' own 0-10 scale). The average is over *the days it was rated*, not over the seven days of the week — a chip the patient never touched is not a rating of nought, and counting it as one would pull every emotion down in proportion to how often they skipped it. Never null: a row exists only because the emotion was rated at least once. The ranking **orders by `avg_intensity`** and the bar length measures it too, against the 0-10 scale itself rather than against the longest row — the section is "Najsilniej odczuwane emocje". It used to rank and draw by `days`, on the argument that a single very bad day should not outrank a feeling that ran through the whole week; that argument is fair about *ordering* and was the wrong one to let decide the *bar*. Week 2026-08-24 is what settled it: 'Smutek' was rated on five days at an average of 0.8/10 and drew a bar 83% as long as the week's strongest feeling, while 'Spokój' at 6.3 drew the same bar as 'Lęk' at 2.5 — a specialist reading those lengths sees a sad week the diary does not describe. Ties break on `days`, then on declaration order. The scale being absolute is the second half of the fix: relative to the top row, the strongest feeling fills the bar whether it averaged 9 or 1.5, so a calm week and a desperate one draw the same picture. `days` stays on every row as the second number, the summary chips still compare it week to week, and the narrative summary now names the *strongest* emotion (`Najsilniej odczuwana emocja: …`) rather than the most frequent — naming a strongest-first row with a frequency would be a false claim in a document a therapist reads. **The ranking is not capped** — every emotion the week rated gets a row, up to the ten the vocabulary holds. An emotion nobody touched simply has no row: absence is what "not felt this week" looks like, and a cut list would read as emotions that were not felt rather than as ones that did not fit. `TOP_TRIGGERS` (4) still caps the other ranking, where the list is unbounded free text.
- **`frontend/src/types/report.ts` is the contract** and the payload is that shape, snake_cased. A `Delta` travels as a structure — signed value, unit, tone, and which of *two* reasons a number is missing (`no-previous-week` vs `unrated`, because saying "there is no previous week" about a week that exists and simply skipped a question would be false in a document a therapist reads). Each surface words it itself: `formatDeltaSentence` for a card, `report_pdf.format_delta` for print, which spells the gap out because a printout cannot be hovered over.
- **Tie-breaks depend on emotion declaration order** being identical in `core/emotions.py` and `frontend/src/utils/emotions.ts`. `test_emotions.py` now pins the order as well as the names.
- **`GET /api/reports/<week-id>/pdf/`** carries a `PdfRenderer` in its `renderer_classes` and overrides `finalize_response`. Neither is decoration: DRF negotiates content *before* the handler runs, so without a renderer declaring `application/pdf` a caller sending `Accept: application/pdf` — which is what `apiDownload` sends — is answered **406** and the view never runs; and once negotiation picks that renderer, a 404 would be served as `application/pdf` (a file the browser offers to save) unless error responses are forced back to JSON. Nothing is ever rendered through `PdfRenderer`; the view returns bytes ReportLab already produced. It answers `application/pdf` with `Content-Disposition: attachment` (an ASCII filename by construction, so no header encoding), `Cache-Control: no-store` (health data leaving as a file must not sit in a cache), and a throttle of its own (`ReportPdfThrottle`, `30/hour` per account) because laying out a document is CPU on a synchronous worker. The document carries **the patient's e-mail**, under the entry count: a printout that reaches a specialist has to say whose week it is. That address is the only thing in it from user_db, and the view reads it off the session at render time — `core/reports.py` aggregates medical_db and never sees one, so the two halves still only meet in application code. Nothing *else* identifying goes in (no `id_medical`, no user id, nothing in the PDF metadata). Note that the fonts are subset, so text is written as glyph codes: **a test that searches the PDF bytes for a string passes whether or not the string is in the document** — assert on `build_story`, which exists for exactly that reason. Everything reaching a `Paragraph` goes through `report_pdf.text()`: ReportLab parses a mini-HTML there, and the 'Inne' trigger and the risky-behaviour note are typed by the patient, so a bare `&` would otherwise fail the export for whoever wrote one.
- **ReportLab, not WeasyPrint.** WeasyPrint would match the web design but needs Pango/Cairo/gdk-pixbuf — ~150 MB of apt on top of `python:3.12-slim` and a Dockerfile change. The document is a heading, four figures, two rankings, a list and a paragraph, which Platypus does with no system dependencies. **`backend/core/fonts/` holds Liberation Sans (SIL OFL), committed**: ReportLab's bundled Vera has no `ą ę ń ś ź ż`, and the slim image ships no fonts at all.
- **`GET /api/reports/`** and **`GET /api/reports/<week-id>/`** are read-only structurally — no write verb exists on either. The detail view builds every report to return one, which is the honest cost of deriving them: a week's numbers are meaningless without the week before it. A week nobody has entries for answers 404, exactly like somebody else's would.

**Both list screens are paginated at 7 rows** (`hooks/usePagination.ts`, `components/Pagination.tsx`). Client-side, and that is a constraint rather than a shortcut: `/api/diary/` and `/api/reports/` answer with everything, and "Dzienniczki" filters what it already holds — paginating on the server while filtering in the browser would hand out pages of the wrong list. So this is a readability feature, not a payload one; the day `MAX_HISTORY_ENTRIES` becomes a real ceiling instead of a backstop, filtering and paging have to move to the backend together.

- The page lives in `?page=`, not in component state, so opening a row from page three and pressing back returns to page three. - **Journals paginates the filtered list and resets to page one when the filter changes** — page four of "Wszystkie" is rarely page four of "Dobre dni", and landing on an empty page reads as "no such days" rather than "wrong page".
- `goTo` scrolls to the top (`RouteChange` only watches the pathname, and this is a query change); `reset` deliberately does not, because a filter chip is pressed from the top already.
- The control renders nothing at one page, and shows prev / "Strona X z Y (a–b z N …)" / next rather than numbered buttons: a year of reports is fifty-odd pages, which is a row of buttons nobody can use on a phone.

**The app shell.** `App.tsx` wraps every route in four things a single-page app has to do by hand, because a real page load does them for free:

- `components/RouteChange.tsx` sets `document.title` from `ROUTE_TITLES` (keyed by route pattern, matched with `matchPath` so `/reports/:id` resolves), scrolls back to the top, and announces the new screen through an `aria-live` region. Titles live in `routes.ts` rather than in each page because the announcement has to happen when the URL changes and a page's own effect runs after that — it would name the screen the user just left. The first render is skipped: the browser has already scrolled and read the document.
- `components/OfflineBanner.tsx` (+ `hooks/useOnline.ts`) says the device is offline. Advisory only — `navigator.onLine` says the device has *a* connection, not that our API answers, so it never gates a request. It exists because every screen words a failure as "Nie udało się wczytać…", which invites an immediate retry and is the wrong advice for a phone in a lift.
- a skip link onto `<main id="main">`. `#main` carries `display: flex; flex-grow: 1` in `index.css` so the `#root > main > .*-page` flex chain still lets a screen fill the viewport.
- `*` renders `pages/NotFound.tsx` instead of redirecting to `/modules`, which made a mistyped address look like it had worked.

`src/index.css` is the global baseline and nothing more. It used to carry the Vite starter's own design system next to the project's — a purple accent, code/social styling, and **`color-scheme: light dark` with a dark palette**, which on a device in dark mode asked the browser to render native controls (date pickers, selects, slider tracks) dark on top of the app's white cards. The app is deliberately light-only. What is left is the font baseline, a zero-specificity `:focus-visible` floor (`:where(...)`, so every screen's own focus style still wins), a `prefers-reduced-motion` block, and `.visually-hidden`/`.skip-link`. `src/App.css` was 180 lines of starter markup styling that nothing imported; it is gone.

**A session that ends while the app is open** is handled by `api/client.ts` dispatching `UNAUTHORIZED_EVENT` on any 401/403 and `auth/AuthProvider.tsx` deciding what it means. The split is the point: the client knows about fetch and cookies and should not learn about React state, and 403 is *also* the normal answer to `/api/auth/me/` for a visitor and the answer to a stale CSRF token. So the provider ignores the event when nobody is signed in, and otherwise **re-asks `/api/auth/me/`** rather than assuming — only a confirmed `null` clears the session. A failed check leaves the user signed in, because a network blip must not throw away a form somebody is filling. Concurrent refusals collapse into one check.

**Leaving "Dodaj wpis" with unsaved changes** asks first. `dirty` compares the draft with the last server-agreed state by value, so a change made and undone is not a change. It covers `beforeunload` (reload, closed tab, back out of the app) and the screen's own back arrow; **a header-menu link still navigates away silently** — `<Routes>` cannot block in-app navigation without a data router. Saving marks the draft clean before navigating, or the guard would ask about the changes just written, and passes `state: { savedEntry: true }` so `/home` renders the confirmation — shown there rather than on the form, which navigates away before a message could be read.

**Frontend/backend wiring.** `frontend/src/api/client.ts` is the only place that knows about `credentials: 'include'` and the `X-CSRFToken` header (including one silent retry with a fresh token on a 403, for when the server restarted). `frontend/src/api/auth.ts` is the single translation point between the form's camelCase field names and the API's snake_case columns, in both directions — including `REGISTER_FIELDS`, which is what lets a Django field error land under the right input. `src/auth/` holds the session context that `App.tsx`'s route guards wait on.

In development the frontend talks to `/api` on its own origin and `vite.config.ts` proxies that to `http://127.0.0.1:8000` (override the target with `API_PROXY_TARGET` in `frontend/.env.local` if Django listens elsewhere). That keeps the session cookie first-party and avoids CORS entirely, but **not** Django's CSRF origin check: the proxy rewrites `Host` to the target, so `http://localhost:5173` has to be in `CSRF_TRUSTED_ORIGINS` or every POST comes back 403 with "Origin checking failed". Pointing `VITE_API_BASE_URL` at a backend on another origin instead makes every call cross-site, which needs `DJANGO_CROSS_SITE_COOKIES=true` on the backend plus the frontend's origin in both `CORS_ALLOWED_ORIGINS` and `CSRF_TRUSTED_ORIGINS`.

## Commands

### Backend (Django)
```bash
source .venv/bin/activate
cd backend
python manage.py runserver
python manage.py createsuperuser        # requires auth_user table -> run migrate first
python manage.py migrate                # applies Django's own built-in app migrations (auth/admin/sessions/contenttypes) to 'default' only
python manage.py makemigrations core    # after changing backend/core/models.py
python manage.py makemigrations --check --dry-run   # verify models.py and migrations are in sync (safe, no DB needed)
python manage.py test core --noinput               # full suite (creates test_user_db + test_medical_db)
python manage.py test core.tests.test_routers      # router/env-config tests only, no database touched
python manage.py check_databases        # both DBs reachable, migrated and in step with models.py (read-only)
```
`migrate core --database=default` / `migrate core --database=medical` create the actual domain tables — see the reconciliation caveat above before running either against a real database.

**`scripts/setup_dev.sh` is the one command that cannot forget the second database**: it migrates `default` *and* `medical` (with `--fake-initial`, since `database_setup.sql` creates the schema) and then runs `check_databases`. Idempotent and data-safe, so it is also the right thing to run after a `git pull` that brought migrations. It deliberately does **not** create or seed the databases — that needs the container and the SQL scripts and is destructive; `markdown/serwery.md` has that sequence.

**`manage.py check_databases` fills the one edge of the schema triangle nothing else covers.** `test_schema_sync.py` compares `database_setup.sql` with `core/models.py`, and `makemigrations --check` compares `models.py` with the migration state — but **nothing compared a real database with the models**, which is precisely where a faked `0001` plus two migration histories goes wrong: a `migrate` that hit `default` only leaves medical_db behind, the imports and the whole test suite still pass, and the first request to `/api/dashboard/home/` answers 500 with `column diary.tension_level does not exist`. The command checks reachability, unapplied migrations per database, every model column against `information_schema` (routed per model, so a medical table is not looked for in user_db), and the `throttle_cache` table — that last one because its absence makes the rate limits **fail open** silently. Read-only and exit-code driven, so it works as a CI step and, more to the point, as the post-deploy smoke test for Azure: `DJANGO_ENV_FILE=.env.azure python manage.py check_databases`. A column the database has and the models do not is a *warning*, not a failure (an un-run `0006` looks exactly like that), or the command would be unusable mid-migration. It is the only module in `core`/`config` allowed to hold a database cursor — `test_security_guards.SqlInjectionSinkTests.CURSOR_ONLY` lists it with its reason and pins that it still runs no statement of its own.

**Backend tests** live in `backend/core/tests/` and use Django's own runner (no pytest, no extra dependency):

- `test_routers.py` — `CoreDatabaseRouter` placement and `allow_migrate` rules, including that operation hints arrive spread as kwargs (`target_db=...`, not `hints={...}`), and that `0002`'s hints still match what the router reads. `SimpleTestCase`, no database.
- `test_models.py` — routing per model, the pseudonymized `id_medical` join (unknown ids accepted, no cascade across databases), the deliberate `PROTECT`/`SET_NULL`/`CASCADE` choices, the `parent_child` constraints, and that `created_at`/`updated_at` come from `auto_now*` rather than DB defaults. Needs both databases.
- `test_env_config.py` — imports `config/settings.py` in a subprocess to check that `DJANGO_ENV_FILE` selects the file, real env vars override it, a missing file is survivable (the App Service case), a missing required key hard-fails, `DB_SSLMODE` defaults to `require`, and that no local env file pairs an `azure.com` host with `sslmode=disable`.
- `test_dashboard_api.py` — `/api/dashboard/home/`: that only the signed-in patient's own rows are aggregated and a non-patient account is refused, how a day's dominant emotion and bar height are chosen (declared emotion first, highest rating as fallback, stress competing with the mood scales), the 7-day window and its averages, the streak's tolerance for an unwritten today, and that an `id_medical` with no rows is an empty dashboard rather than an error. Needs both databases.
- `test_auth_api.py` — the `/api/auth/` endpoints: what registration writes (hash not password, consent timestamps, `Patient` row, `patient` role, and that a missing role row is survivable), that login is case-insensitive on e-mail and indistinguishable between a wrong password and an unknown address, that a non-hash `password_hash` fails cleanly rather than 500-ing, the session lifecycle including a cookie pointing at a deleted user, throttling, and that CSRF is actually required on login/register/logout. `default` only.

- `test_guardian_api.py` — the invitation flow: that only a `rodzic` account's address is accepted (a patient's, a specialist's, a role-less account's and an unregistered one are all refused identically), that inviting creates `accepted_at` NULL and leaves the child blocked, that only a minor patient may invite and the child comes from the session rather than the body, that the child can withdraw a pending invitation but not an accepted link, that **the child cannot accept their own invitation** and another guardian's answers 404, that accepting is idempotent while refusing deletes the row, and that `guardian_status` is `null` for everyone the question does not apply to. `default` only.

- `test_account_api.py` — `/api/account/`: that the counters match what `/api/diary/` and `/api/dashboard/home/` answer with rather than being computed twice, that a streak ending yesterday still counts, that an unassigned patient gets `care: null` and a specialist with no name falls back to their address, that `phone` is null because no column holds one, that the consent timestamps reach `/api/auth/me/` for every account including a guardian's while an ungranted one stays null — and, on `password/`, that a wrong current password changes nothing and is named plainly, that a short *current* password is not refused for being short, that reusing the current password is a request-level error, that the new one goes through Django's validators including the similarity one, that the session survives, that a guardian may change theirs, and that guessing is capped. Needs both databases.
- `test_consent_gate.py` — the consent gate: that **every** registered URL but the four escape hatches answers 403 to an account whose consents are not in force, that the refusal names what is missing and carries no data, that a refused write writes nothing, that one missing consent is enough, that an account which never granted one meets the same screen and can grant it from there, that restoring reopens the clinical endpoints — and, on the two endpoints, that withdrawing does not erase the grant, that withdrawing twice keeps the first moment, that restoring writes a later grant without hiding the withdrawal, that restoring an active consent does not move its date, that **nothing is deleted** and the diary is there again afterwards, and that the consent gate answers before the guardian one for a minor behind both. Needs both databases.
- `test_guardian_gate.py` — the gate on the API: that an unlinked minor (none named, or named and unanswered) is refused on **every** clinical URL, that acceptance opens all of them and a refusal closes them again, that the way out of the gate stays reachable from inside it (`auth/guardian/`, `me/`, `logout/`), that a refused PUT writes nothing, that an adult patient and an `is_child` NULL row are not gated while a guardian keeps the older "no patient row" refusal, and that the gate is checked before an entry id is looked up so the answer leaks nothing about whether the row exists. Needs both databases.
- `test_check_databases.py` — the `check_databases` command, every test of which breaks the schema on purpose (the DDL rolls back with the test transaction): that a missing column is reported **with the database it is missing from** and with the `--database=` flag to fix it, that several are listed in one run, that a missing domain or cache table is caught, that an extra column is a warning rather than a failure, that model→database routing is respected so nine tables are not reported missing from the wrong database, and that `--quiet` hides the OK lines but never a finding. Needs both databases.
- `test_days.py` — the calendar-day boundary in `settings.TIME_ZONE` rather than UTC, which decides what "today" means for the streak and for the one-entry-per-day rule. No database.
- `test_emotions.py` — the ten-name vocabulary, including a **cross-language check that `frontend/src/utils/emotions.ts` declares character-for-character the same names**. Nothing else enforces that agreement. Also covers `normalize_emotion`, including Polish `ł`, which NFKD cannot decompose. No database.
- `test_diary_unit.py` — the decisions under `/api/diary/today/`: which emotion counts as strongest (and that its tie-break matches `dashboard._ratings`), the mood-label round trip through `current_mood`, and what an empty text box means. No database.
- `test_schema_sync.py` — the drift `makemigrations` cannot see, because `0001` is faked: parses `scripts/database_setup.sql` (CREATE TABLE plus its ALTER blocks) and compares column-for-column with `core.models`, in both directions, per table. Also checks that every column `mock_data.sql` inserts into still exists. No database.
- `test_throttling.py` — what the throttle writes into the cache key: that the caller's IP is hashed rather than stored, that the digest is keyed on `SECRET_KEY` (a bare SHA-256 of an IPv4 address is exhaustible), that the same caller still lands on the same counter, and that a request with no address at all does not raise. The caps themselves are covered where the endpoints are. No database.
- `test_migrations.py` — that every raw-SQL migration carries a `target_db` hint pointing at the right database, is reversible, tolerates the columns already existing (the documented setup order runs the SQL script first), and that the two halves of each `SeparateDatabaseAndState` describe the same change. No database.

- `test_reports_api.py` — `/api/reports/`, exhaustively: which weeks get a report (the one in progress, empty ones and future-dated rows do not), the **week boundary in Europe/Warsaw** (23:59 Sunday vs 00:30 Monday — the case a UTC boundary files into an already-generated report), gaps between weeks, two entries in one day, more than one `mood_scale` row, the `TOP_EMOTIONS`/`TOP_TRIGGERS`/`SUMMARY_CHIP_EMOTIONS`/`MAX_HISTORY_ENTRIES` limits, every branch of both delta kinds and both gap reasons, the summary's Polish declensions, id handling (a Tuesday, no prefix, wrong case, a slash, 500 characters), who may ask, and that the payload is the documented shape and JSON-serialisable. - `test_report_pdf.py` — the PDF: that it renders, that rendering twice does not trip the global font registry, that **the font actually in use covers Polish** (invisible in a byte count, and ReportLab's default does not), the printed delta wording, the document's content read off `build_story` (never off the bytes — see below), a full week of flagged days spilling onto a second page, every section empty at once, escaping of what the patient typed, and on the endpoint: Accept negotiation, throttling, no write verbs, and that two accounts do not get identical bytes for the same week. Mostly no database.
- `test_diary_history_api.py` — `/api/diary/` and `/api/diary/<id>/`: that the list holds only the signed-in patient's entries newest-first, that another patient's entry answers 404 rather than 403 (a 403 would confirm it exists), and that neither URL accepts a write verb. Needs both databases.

Always pass `--noinput`: an aborted run leaves `test_user_db` behind and the next run then blocks on an interactive "delete it?" prompt, producing no output at all. Test databases are built from migrations (not `database_setup.sql`), so `0001` runs for real there rather than faked.

## Infrastructure

Backend dev deployment runs on Azure App Service (`mediculus-dev`), backed by Azure Postgres (two databases as above), with credentials/registry info supplied via `.env`-style App Settings (`DJANGO_REGISTRY_NAME`, `DJANGO_LOGIN_SERVER`, `DJANGO_USERNAME`, `DJANGO_PASSWORD` are ACR credentials, not app credentials). Treat DB and ACR passwords as live secrets — they are not meant to be pasted into chat/commits.
